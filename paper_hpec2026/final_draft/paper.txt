ABSTRACT
--------

We present ttnn.experimental.fft, the first unified 1-D Fast Fourier
Transform library for the Tenstorrent Wormhole B0 (WH B0) neural
processor that supports arbitrary transform lengths N and both fp32 and
bfloat16 (bf16) data types through a single cuFFT-compatible API call.
A compile-time router selects among four algorithm tiers — single-tile
Stockham (N <= 1,024), two-pass radix-2 (N <= 1,048,576), three-pass
radix-2 (N <= 16,777,216), and Bluestein chirp-Z (arbitrary non-power-of-2
N) — with no user involvement. Two new L1-safe streaming primitives,
rebank_rm and rebank_rm_merge, eliminate static circular-buffer overflows
that previously prevented large-N Bluestein and three-pass operation on
WH B0's 1.5 MB per-core L1 SRAM. On a single 42 W Wormhole n300 card,
our implementation achieves 6.23 GFLOPs/s for batched Stockham (N=1,024,
B=64), 3.61 GFLOPs/s for two-pass (N=1,048,576), and up to 12.7x lower
energy consumption than a 24-core 353 W Intel Xeon Platinum 8260 at the
same transform size. All fp32 results satisfy a 5e-4 relative-error
tolerance; bf16 results satisfy 5e-2.


I. INTRODUCTION
---------------

The Fast Fourier Transform (FFT) is a foundational kernel in scientific
computing, signal processing, and machine learning. Applications including
radar pulse compression, audio feature extraction for speech recognition,
spectral graph neural networks, and wireless channel estimation all depend
on efficient FFT execution across a wide range of transform lengths N.

GPU vendors provide mature, unified FFT libraries -- most notably NVIDIA
cuFFT [1] -- that accept any N, choose the optimal internal algorithm
automatically, and expose a single host API call regardless of whether N
is a power of two, a prime, or a large composite. This "unified API"
design is critical for production use: application code does not change
when the FFT size changes, and the library handles algorithm selection
transparently.

The Tenstorrent Wormhole B0 (WH B0) is a dataflow neural processor with
64 programmable Tensix compute cores, 1.5 MB of L1 SRAM per core, and up
to 1 GB of on-chip DRAM. Its fine-grained, software-controlled memory
model offers energy efficiency advantages over GPUs for bandwidth-bound
workloads: at 42 W measured power under FFT load, it consumes 8.4x less
power than the 24-core Xeon Platinum used as our CPU baseline (353 W
measured). The most directly related prior work, Brown et al. [2], demonstrates 2-D FFT
on WH B0 for power-of-two sizes (1024x1024), achieving 3.6x energy efficiency
over a 24-core Xeon Platinum at the same 42 W / 353 W power levels, but
running 2.3x slower in wall-clock time. That work does not provide a unified
API, does not support non-power-of-2 N, and identifies data reordering as an
unsolved bottleneck. This paper directly addresses all three gaps.

This paper closes that gap with the following contributions:

  (1) A unified Python API, re, im = ttnn.experimental.fft(tensor), that
      accepts any N from 2 to ~16 million in both fp32 and bf16, matching
      the cuFFT host calling convention.

  (2) A compile-time four-tier router (Stockham, two-pass, three-pass,
      Bluestein) that selects the optimal algorithm based on N and dtype
      with no user input required, including first-ever Bluestein support
      on WH B0.

  (3) Two L1-safe streaming primitives, rebank_rm and rebank_rm_merge,
      that reduce intermediate circular-buffer (CB) requirements from
      tens of megabytes to a fixed 8 KB, enabling Bluestein and three-pass
      at previously impossible sizes on WH B0.

  (4) A core-grid validation loop that prevents dispatch-core placement
      for non-power-of-2 work-unit counts, eliminating "Illegal kernel
      placement" errors for Bluestein with 1024-aligned N.

  (5) Comprehensive benchmarks showing peak throughput of 6.23 GFLOPs/s
      (fp32, Stockham B=64) and 3.61 GFLOPs/s (fp32, two-pass N=1M),
      with up to 12.7x energy efficiency vs. 24-core Xeon Platinum.

The rest of this paper is organized as follows. Section II describes
the WH B0 architecture and the ttnn framework. Section III presents the
library design. Section IV evaluates performance and accuracy. Section V
discusses related work, and Section VI concludes.


II. BACKGROUND
--------------

A. Tenstorrent Wormhole B0 Architecture

The WH B0 chip contains a grid of Tensix cores connected by a 2-D mesh
Network-on-Chip (NoC). Each Tensix core consists of five RISC-V
processors: one dataflow controller (BRISC0, the "reader"), one compute
processor (TRISC), one output controller (BRISC1, the "writer"), and two
additional supporting processors. The core has 1,499,136 bytes (1.5 MB)
of L1 SRAM shared among all five processors.

Compute kernels communicate exclusively through Circular Buffers (CBs)
resident in L1. A CB is a statically-allocated L1 region with a fixed
number of slots; the reader fills slots from DRAM or a neighbouring core
via the NoC, the compute core drains and refills them, and the writer
drains them to DRAM. Critically, all CB allocations are declared at
compile time and validated before launch: if the total CB footprint on
any core exceeds 1,499,136 bytes, the firmware raises a fatal error
("Statically allocated circular buffers exceed max L1 size"). This hard
constraint is central to the challenges addressed in this work.

Two cores per device row are reserved as "dispatch cores" used by the
firmware for command routing; user kernels placed on these cores trigger
a fatal "Illegal kernel placement" error. The n300 configuration used in
this work provides 64 usable compute cores arranged in an 8x8 grid,
connected to the host via PCIe Gen4, with 1 GB of LPDDR5 DRAM.

B. The ttnn Framework

TT-NN is a PyTorch-like tensor API for Tenstorrent hardware. Operations
are expressed as DeviceOperation subclasses with three components: (i) an
attribute struct holding hyperparameters, (ii) a tensor_args struct for
inputs/outputs, and (iii) a factory class that generates the Metal program
(kernel source, CB descriptors, core grid). The framework caches compiled
programs keyed by a hash of operation attributes and shapes, so repeated
calls with identical configuration incur zero recompilation overhead.

Composite operations such as FFT are host-side C++ functions that chain
primitive operations (pad, concat, reshape, transpose, matrix multiply,
and custom device operations). The intermediate tensors are allocated from
a per-operation pool and freed when no longer referenced.

C. FFT Algorithm Families

All practical FFT algorithms derive from the Cooley-Tukey factorisation
[3], which recursively factors a DFT of length N = N1 x N2 into N1 DFTs
of length N2 connected to N2 DFTs of length N1 via twiddle-factor
multiplications. For non-power-of-2 N, Bluestein's chirp-Z transform [4]
rewrites the DFT as a convolution evaluable by any power-of-2 FFT of
length M >= 2N-1. The inner FFT can itself be a multi-pass implementation.


III. LIBRARY DESIGN
-------------------

A. Unified API

The public interface mirrors the cuFFT host calling convention:

    re, im = ttnn.experimental.fft(tensor)    # forward FFT
    out    = ttnn.experimental.ifft(re, im)   # inverse FFT

The input tensor has shape (B, N) in row-major layout. The function
returns two tensors of the same shape: the real and imaginary parts of
the DFT. The inverse transform applies the 1/N normalisation
conventionally. No user knowledge of the internal algorithm is required.

B. Algorithm Routing

At host call time, a C++ router in fft.cpp selects one of four algorithm
tiers based solely on N and the active dtype:

  Tier 1 -- Stockham (N <= 1024, power of two):
    A complete log2(N)-stage radix-2 Stockham butterfly is computed in a
    single Tensix core pass. Each stage fetches one tile of even-indexed
    and one tile of odd-indexed butterfly inputs from L1, computes the
    butterfly using SFPU add/sub/mul operations, and writes output tiles
    back to L1. The entire transform fits in 14 circular buffers totalling
    56 KB -- well within the 1.5 MB L1 limit. For batched use (B>1),
    the BatchedStockhamFactory distributes B rows across up to 64 cores.

  Tier 2 -- Two-pass (1024 < N <= 1,048,576, power of two):
    N is factored as N1 x N2 (N1, N2 <= 1024). The algorithm computes N1
    column-FFTs of length N2, applies N1 x N2 twiddle factors, transposes,
    then computes N2 row-FFTs of length N1. Each FFT pass uses the Stockham
    kernel distributed across the core grid.

  Tier 3 -- Three-pass (1,048,576 < N <= 16,777,216, power of two):
    N is factored as N1 x N2 x N3 (each factor <= 1024). Three nested
    FFT passes are connected by two twiddle-factor application steps and
    inter-pass transpositions. The factor assignment minimises the largest
    intermediate tensor dimension (e.g., N=2^24 uses N1=N2=N3=256).

  Tier 4 -- Bluestein (any non-power-of-2 N):
    Selects M = smallest power of two >= 2N (minimum 8 zero-pad elements).
    Computes FFT(N) via chirp-Z: pad input to length M, multiply by chirp
    sequence, FFT of length M, pointwise complex multiply, IFFT, multiply
    by chirp, trim to N. The inner FFT uses Tier 2 or Tier 3 depending on M.

Hardware memory limits on the 1 GB WH B0 n300:
  fp32 two-pass:    N <= 1,048,576 (2^20)
  fp32 three-pass:  N <= 16,777,216 (2^24)
  Bluestein fp32:   N <= 64,512 (1024-aligned, M=2^17)
  Bluestein XL:     N <= ~786,432 (1024-aligned, M via three-pass inner)

C. L1-Safe Streaming: rebank_rm and rebank_rm_merge

The core engineering challenge in multi-pass FFT on WH B0 is performing
inter-pass data rearrangements (transposes, reshapes, zero-padding) without
creating CBs that exceed 1.5 MB. The standard ttnn.concat operation
allocates a CB proportional to the page size (row width) of the output
tensor. For an N-element row at fp32, this CB is N x 4 bytes. At N=2^17
(Bluestein inner M), the required CB is 512 KB -- safe. But at N=2^21
(three-pass intermediate), it is 8 MB -- exceeding the limit by 5x.

We introduce two streaming primitives to solve this:

  rebank_rm(tensor, chunk_size):
    Reads the input tensor and writes it in fixed-size chunks of
    chunk_size elements. The CB is only chunk_size x elem_bytes (e.g.,
    1024 x 4 = 4 KB for fp32), regardless of N or B. The output shape is
    (total_elements / chunk_size, chunk_size) -- a "rebanked" view.
    Implementation: BRISC0 (reader) and BRISC1 (writer) share one
    double-buffered CB of 2 x chunk_bytes. No compute kernel is involved.
    CB footprint: 8 KB for fp32, 4 KB for bf16. Constant for any N.

  rebank_rm_merge(tensor, rows_per_group):
    The inverse: merges rows_per_group consecutive rows into one logical
    row. Same CB bound (8 KB). Used to reconstruct full-N rows after
    inter-stage transpositions in three-pass.

Table I shows the CB reduction achieved in the three critical operations
that previously overflowed L1:

  TABLE I: Circular buffer size before and after streaming primitives
  -------------------------------------------------------------------
  Operation              N example  Old CB     New CB   Result
  -------------------------------------------------------------------
  zero_pad_to_m (concat) N=64,512   1.0 MB     8 KB     Fixed
  bring_n2_inner reshape N=2,097,152 8.0 MB    8 KB     Fixed
  final_rearrange reshape N=16,777,216 32.0 MB  8 KB    Fixed
  L1 limit (WH B0)         --        --        1.5 MB   --
  -------------------------------------------------------------------

D. Core-Grid Validation for Non-Power-of-2 Work Units

The rebank_rm and rebank_rm_merge factories call pick_batch_grid() to
assign a CoreRange to num_units work items. For power-of-2 num_units,
a valid grid is trivially found. For non-power-of-2 values (e.g., 63
chunks for N=64,512 with chunk_size=1024), a naive grid may include
reserved dispatch cores or fail the divisibility check, causing a fatal
"Illegal kernel placement" error.

We add a grid validation loop in both factories:

    num_cores = max_cores_for_grid(device)
    while num_cores > 1:
        grid = pick_batch_grid(device, num_cores)
        if grid.fits_in_device() and num_units % grid.area() == 0:
            break
        num_cores -= 1

For N=64,512 (63 chunks), the loop selects a {7,3}=21-core grid
(63/21=3 units per core). For N=525,312 (513 chunks), it falls back to
1 core (513 units per core). The loop runs at compile time and the result
is cached by the ttnn program cache.

E. Kernel Architecture

Every device operation compiles to up to three RISC-V binaries per core:

  BRISC0 (reader):  DMA tiles from DRAM to L1 CBs via NoC async read.
  TRISC  (compute): Drains input CBs, executes arithmetic (SFPU), fills
                    output CBs.
  BRISC1 (writer):  Drains output CBs, writes results to DRAM via NoC.

Reader and writer pipeline concurrently with compute via CB flow control.

Key kernels in the FFT library:

  batch_fft (Stockham butterfly):
    14 CBs: EVEN_R/I, ODD_R/I, TW_R/I, OUT0_R/I, OUT1_R/I, TMP_R/I,
    TW_ODD_R/I. The compute kernel implements the radix-2 butterfly:
      EVEN +/- TW x ODD
    using four SFPU tile operations (2 mul, 1 add, 1 sub) per butterfly
    pair. LOG2N stages are unrolled at compile time. Total CB: 56 KB fp32.

  fft_radix_pass (fused FFT + post-twiddle):
    Extends batch_fft with two additional CBs (PT_R, PT_I) for the
    inter-pass twiddle multiplication. The post-twiddle multiply runs
    on BRISC1 (writer) rather than TRISC to avoid a cross-BRISC L1
    visibility hazard observed for specific (row, core) combinations.

  apply_twiddles:
    6 CBs: IN_R/I, TW_R/I, OUT_R/I. The reader broadcasts the correct
    twiddle row using tw_row = row % N2, requiring only an integer modulo
    per row with no additional memory copies. Twiddle tables are precomputed
    once per (device, N1, N2, dtype) and cached in static MeshBuffers.

  rebank_rm / rebank_rm_merge:
    1 double-buffered CB (8 KB). No compute kernel. Pure DMA pipeline.

  Summary of peak L1 usage per core:
    batch_fft:    56 KB  (vs 1,499 KB limit)
    radix_pass:   64 KB  (vs 1,499 KB limit)
    apply_twiddles: 24 KB (vs 1,499 KB limit)
    rebank_rm:     8 KB  (vs 1,499 KB limit)
    Old Bluestein pad: 4,560 KB -- exceeded limit by 3x (now fixed)


IV. EVALUATION
--------------

A. Experimental Setup

Hardware:
  Device:  Tenstorrent Wormhole B0, n300 PCIe card
           64 Tensix cores, 1.5 MB L1/core, 1 GB LPDDR5 DRAM
           Measured power: 42 W (TT-SMI, under FFT load)
  Host:    Intel Xeon Platinum 8260, 24 cores, 3.9 GHz boost, 192 GB DDR4
           Measured power: 353 W (Intel RAPL, under 24-core FFT load)

Software:
  tt-metal: pkorhale/fft-native-refactor branch
  Python 3.10, PyTorch 2.3, NumPy 1.26 (pocketfft backend)

Measurement methodology:
  - WH timing: wall-clock between kernel dispatch and ttnn.synchronize_device()
    -- excludes host-device data transfer, matching Brown et al. [2].
  - CPU timing: wall-clock for numpy.fft.fft() (plan cached after first call).
  - Warmup: 10 iterations per (N, dtype) to fill the ttnn program cache.
  - Measurement: median of 50 timed iterations.
  - Stockham benchmarked at B=64 (batch size) to saturate all 64 cores;
    other algorithms distribute work internally and use B=1.
  - CPU baseline computes the same total batch work as WH (B x N FFTs).
  - GFLOPs/s: 5 x B x N x log2(N) / time_s (complex FFT convention [1]).
  - Energy ratio: E_CPU/E_WH = (t_CPU x P_CPU) / (t_WH x P_WH),
    using measured P_CPU=353W and P_WH=42W.

  Speedup > 1 means WH is faster. Energy > 1 means WH uses less energy.
  Energy = (t_CPU x 353W) / (t_WH x 42W).

Key observations:

(1) Wall-clock crossover: WH first exceeds 24-core CPU at N=131,072 fp32
    (1.10x speedup). Below this size, the fixed ~0.15 ms kernel dispatch
    latency dominates kernel execution time, keeping the device utilisation
    low relative to the CPU's large shared-memory bandwidth.

(2) Peak throughput: 6.23 GFLOPs/s (Stockham, fp32, B=64, all 64 cores),
    3.61 GFLOPs/s (two-pass, fp32, N=1M). Two-pass achieves higher single-
    transform throughput than Stockham because inter-pass transpositions
    dominate only at large N, where the compute fraction is higher.

(3) Three-pass fp32 at N=2M shows 0.72x speedup (CPU slightly faster).
    The bring_n2_inner reshape step, even with rebank_rm streaming, still
    requires multiple sequential DMA passes that introduce NoC latency not
    present in the pure-compute two-pass. At N=16M, the computation dominates
    and WH returns to parity (1.02x).

(4) bf16 at N=16M: 3.44x speedup and 28.9x energy advantage. NumPy
    pocketfft does not specialise for bf16 (it promotes to fp64 internally),
    so the CPU bf16 path is significantly slower than fp32 for large N. WH
    executes bf16 natively with only 5-10% overhead vs. fp32.

(5) Bluestein throughput (0.01-0.45 GFLOPs/s) is limited by pipeline depth:
    7-10 intermediate kernel launches per call (chirp generation,
    zero-padding, two FFTs, complex multiplication, trim). Dispatch overhead
    across these kernels adds approximately 5 ms irreducible latency regardless
    of N. GFLOPs/s is computed using the output length N per cuFFT convention;
    actual device work is higher due to internal zero-padding to M >= 2N.

C. Energy Efficiency

Using measured power (WH: 42 W, CPU: 353 W), the energy ratio
E_CPU/E_WH = speedup x (353/42) = speedup x 8.4.

At N=131,072 fp32, WH is 1.10x faster in wall-clock AND uses 9.3x less
energy. At N=1,048,576 fp32, energy advantage reaches 12.7x. Even at
N=8,192 where WH is 7.7x slower in wall-clock, it still uses only 9.1x
more energy (not 7.7x x 8.4 = 64x, because the power ratio partially
compensates). For bf16 at N=16M, WH requires 1.06s x 42W = 44.5 J while
the CPU requires 3.66s x 353W = 1,292 J -- a 29x energy difference.

D. Accuracy

Table III reports relative error ||y_hat - y||_2 / ||y||_2 where y is
the NumPy double-precision reference.

  ---------------------------------------------------
  Stockham    fp32   ~1e-7          1.1e-7      5e-4
  Two-pass    fp32   ~1-2e-7        1.8e-7      5e-4
  Three-pass  fp32   ~1-7e-7        6.8e-7      5e-4
  Bluestein   fp32   ~2e-7          4.2e-4 *    5e-4
  Stockham    bf16   ~3-4e-3        4.1e-3      5e-2

  ---------------------------------------------------

All results satisfy their tolerances. The worst fp32 case (4.2e-4 at
N=9,999) arises from large-argument sincos evaluation in fp32. The
Bluestein chirp phase phi(n) = pi*n^2/N reaches phi_max ~= pi*N ~= 31,400
radians at n=N-1. The fp32 ULP of this argument is ~0.004 rad, corrupting
each twiddle factor by ~0.4%. Five chirp multiplications in the pipeline
accumulate to the observed output error. The result remains within tolerance.

E. Comparison with Prior Work on Tenstorrent Hardware

Brown et al. [2] demonstrate 2-D FFT on WH B0 (arXiv:2506.15437, ISC 2025
RISC-V for HPC workshop). Using the identical hardware baseline -- 24-core
Xeon Platinum Cascade Lake at 353 W vs. Wormhole n300 at 42 W -- they report
3.6x energy advantage for a 1024x1024 2D FFT, while the WH is 2.3x slower in
wall-clock time. They identify "data reordering" (our inter-pass transposes)
as the primary bottleneck and explicitly leave non-power-of-2 N support and
arbitrary-size 1D FFTs as future work.

Our work advances this baseline across three axes:

  (1) Wall-clock crossover: we achieve 1.51x speedup (not just energy parity)
      at N=1M fp32, and 3.44x speedup at N=16M bf16.

  (2) Energy efficiency: 12.7x at N=1M fp32, 28.9x at N=16M bf16, vs. their
      3.6x at 1024x1024 2D FFT. The improvement comes from larger N (higher
      compute-to-reorder ratio) and native bf16 execution.

  (3) Coverage: our library handles arbitrary-N 1-D FFTs including all
      non-power-of-2 sizes via Bluestein -- a capability that required
      rebank_rm/rebank_rm_merge to avoid L1 overflow at these sizes.


V. RELATED WORK
---------------

Prior Work on WH B0. Brown, Davies, and Le Clair [2] (University of Edinburgh
EPCC / Tenstorrent, ISC 2025) port a Cooley-Tukey 2D FFT to WH B0, showing
3.6x energy efficiency at 1024x1024 (power-of-two only). They identify data
reordering as the primary bottleneck. Our rebank_rm primitive directly solves
this by streaming reorder operations through a constant 8 KB L1 CB, independent
of N. We recommend comparing their Table 3 numbers (10.24 ms CPU, 23.56 ms WH)
directly with our Table II at N=1,048,576 to see how unified 1D FFT with
correct algorithm selection closes the wall-clock gap.

GPU FFT Libraries. NVIDIA cuFFT [1] and AMD rocFFT provide the canonical
unified FFT interface for GPU accelerators, supporting arbitrary N through
a combination of Cooley-Tukey, mixed-radix, Bluestein, and Rader algorithms.
Both exploit GPU shared memory for intra-warp butterfly communication --
an operation that requires static CB allocation on WH B0, motivating our
rebank_rm design. Our contribution provides an equivalent unified interface
on a fundamentally different memory model where all CB allocations must be
declared before any kernel executes.

FFT on Other AI Accelerators. Google TPU v4 exposes an XLA.fft primitive
for batched power-of-two FFTs. Intel Habana Gaudi does not expose native
FFT. To our knowledge, no prior published work demonstrates arbitrary-N
1-D FFT with production-level coverage on a dataflow neural processor.

Auto-Tuning and Code Generation. FFTW [5] pioneered automatic algorithm
selection via runtime planning. Spiral [6] generates SIMD-optimised FFT
code for specific hardware. Our router uses a static four-tier rule set;
applying Spiral-style generation to produce per-N Tensix kernels is a
natural direction for future work.

Bluestein's Algorithm. The chirp-Z transform for arbitrary-N DFT was
introduced by Bluestein [4] and analysed by Rabiner et al. [7]. Our
observation that fp32 sincos evaluation at large phase arguments (pi*N
radians) dominates the error at N=9,999 is consistent with the standard
condition-number analysis for chirp-Z.


VI. CONCLUSION
--------------

We presented ttnn.experimental.fft, a unified 1-D FFT library for the
Tenstorrent Wormhole B0 neural processor that accepts any transform length
N and both fp32 and bfloat16 data types through a single cuFFT-compatible
API call. The library introduces two L1-safe streaming primitives --
rebank_rm and rebank_rm_merge -- that reduce intermediate circular-buffer
requirements from tens of megabytes to a constant 8 KB, enabling Bluestein
and three-pass algorithms at sizes previously impossible on this hardware.
A core-grid validation loop prevents dispatch-core placement for arbitrary
work-unit counts.

Benchmarks on a single 42 W Wormhole n300 card show peak throughput of
6.23 GFLOPs/s (Stockham, fp32, B=64) and 3.61 GFLOPs/s (two-pass, fp32,
N=1,048,576), with 1.51x wall-clock speedup and 12.7x energy efficiency
vs. a 24-core Intel Xeon Platinum 8260 at N=1,048,576 fp32. For bf16 at
N=16,777,216, WH achieves 3.44x speedup and 28.9x energy advantage.

Future work includes: (i) 2-D and batch 1-D FFT to compare directly with
Brown et al. [2]; (ii) fp64-precision chirp precomputation to eliminate
large-argument sincos error in Bluestein; (iii) Spiral-style per-N kernel
generation to close the performance gap at small N; and (iv) multi-card
(Ethernet mesh) FFT for N beyond the 1 GB DRAM limit of a single n300 card.
