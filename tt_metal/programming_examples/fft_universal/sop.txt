===============================================================================
 fft_universal — Standard Operating Procedure
===============================================================================

Scope
-----
fft_universal extends the existing power-of-two FFT family (fft/, fft_bf16/,
fft_stockham/) to any input length N >= 2. Every compute path ends on
Wormhole; the host only reshapes, dispatches, and stitches results. It
reuses fft_stockham's Stockham kernels for pow2 sub-FFTs of length >= 64
and adds one new packed direct-DFT kernel for small leaves (len <= 32).

Dispatch summary (all non-identity paths execute on Wormhole):
    len <= 32   (any structure)   : PACKED DIRECT-DFT kernel (Opt #5, below)
    N is power of 2, len > 32     : fft_stockham::fft / batch_fft
    N is prime    (>= 37)         : Bluestein -> 2 pow2 FFTs on device
    N is composite non-pow2       : Cooley-Tukey split, recurse (leaves fall
                                    into the packed path or batch_fft)

Batched recursion (Opt #2 + #2b):
    The engine operates on BATCHES of sibling signals at every level, not one
    signal at a time. A Cooley-Tukey split of (count, N = N1*N2) produces
    (count * N1) siblings for pass-1 and (count * N2) for pass-2 - so batching
    width ACCUMULATES as the recursion descends. A batched Bluestein fuses K
    sibling length-N prime FFTs into exactly 2 device dispatches (pow2 length
    M = next_pow2(2N-1)) regardless of K.

    Consequence: the total number of device dispatches for any composite N is
    O(log N) - independent of the number of siblings at any level.

    Example (N = 3600 = 16 * 225, where 225 = 9 * 25, 25 = 5 * 5):
      * top pass-2:     225 length-16 FFTs     -> 1 batched dispatch
      * 1200 length-3 Bluesteins (inner)       -> 2 batched dispatches
      * 1200 length-3 Bluesteins (other inner) -> 2 batched dispatches
      * 720  length-5 Bluesteins               -> 2 batched dispatches
      * 720  length-5 Bluesteins               -> 2 batched dispatches
    Total: ~9 dispatches, not hundreds.

Host-scratch caching (Opt #4):
    Each batched dispatch through fft_stockham::batch_fft used to allocate and
    zero-init 2 * batch * kTileElems floats of host scratch per call - up to
    16 MB per dispatch for batch=2048 with sub_N=8 (~150 MB allocator+memset
    churn per N=3600 iteration). The host scratch is now owned by the plan
    and reused across calls; zero-init happens exactly once at plan build
    time. The batch-FFT reader/compute only touch the first `sub_N` slots of
    each tile, so pad positions stay valid for the life of the plan. Same
    pattern applied to Pass2Plan for the large pow2 Stockham path.

Packed direct-DFT kernel (Opt #5):
    New device kernel trio under fft_universal/kernel/ — packed_dft_reader,
    packed_dft_compute, packed_dft_writer — targets every sub-FFT of length
    len <= 32. Instead of fft_stockham::batch_fft's "one sub-FFT per tile"
    layout (which for len=8 wastes 99.2% of each tile on padding zeros), we
    pack 32 sub-FFTs per tile (one sub-FFT per tile row, cols [0,len)
    valid, [len,32) zero) and compute the direct DFT as a complex 32x32
    matmul against a cached twiddle matrix T[n,k] = exp(-2*pi*i*k*n/len).

    Complex matmul = 4 real matmuls:
        out_R = in_R * T_R  +  in_I * (-T_I)     (accumulate into DST(0))
        out_I = in_R * T_I  +  in_I * T_R         (accumulate into DST(0))
    The host pre-negates T_I once so every matmul on device ADDS into DST
    (no SFPU subtract needed). Uses the FPU matmul_tiles() LLK at HiFi4 with
    fp32_dest_acc_en=true.

    Gotcha (don't set UnpackToDestFp32 on a matmul kernel):
      The ComputeConfig for this kernel intentionally leaves
      unpack_to_dest_mode at its default. UnpackToDestFp32 routes unpacked
      tiles straight into DST (used by SFPU-style kernels like
      pass2_compute). On a matmul kernel that mode bypasses srcA/srcB,
      so matmul_tiles() reads uninitialised srcA/srcB registers and the
      FPU multiplies garbage, producing 1e28 / inf outputs. The standard
      matmul_single_core example omits unpack_to_dest_mode for exactly
      this reason; mirror that here.

    Why it helps:
      * Tile efficiency jumps from len/1024 (~1-3%) to len/32 (~6-100%).
      * Replaces BOTH small-pow2 batch_fft AND small-prime Bluestein (which
        was 2 dispatches at M up to 64, each worse than the packed path).
      * For N = 3600 the inner-most Bluestein leaves (len=3, len=5) were the
        biggest PCIe hog — they're now single-dispatch, ~30x less PCIe bytes.

    Cache: keyed on (MeshDevice, N, count). Same host-scratch-reuse pattern
    as Opt #4 (buffers live on the plan, zero-init once).

-------------------------------------------------------------------------------
 Build
-------------------------------------------------------------------------------
Top-level programming_examples CMakeLists.txt registers the folder. Build all
three executables with:

    ninja -C build \
        metal_example_fft_universal_test \
        metal_example_fft_universal_benchmark \
        metal_example_fft_universal_demo

Binaries land in:

    build/programming_examples/fft_universal/
        metal_example_fft_universal_test
        metal_example_fft_universal_benchmark
        metal_example_fft_universal_demo

-------------------------------------------------------------------------------
 Run correctness tests
-------------------------------------------------------------------------------
Validates against a double-precision DFT reference across a mix of sizes:

    ./build/programming_examples/fft_universal/metal_example_fft_universal_test

Sizes covered include:
    * power-of-two N (fall-through)          : 1024, 16384, 65536, 131072
    * small composite non-pow2               : 6, 12, 24, 36, 360
    * highly composite                        : 720, 1000, 1800, 3600
    * prime N (Bluestein path)                : 5, 7, 11, 17, 97, 101, 1021
    * composite with a large prime factor    : 2*101 = 202, 3*97 = 291
    * 2 * prime                               : 2*257, 2*509

-------------------------------------------------------------------------------
 Run benchmark
-------------------------------------------------------------------------------

    ./build/programming_examples/fft_universal/metal_example_fft_universal_benchmark [N] [iters]

Defaults: N = 1000, iters = 100. N can be anything >= 2.

Output columns are the same as the other fft benchmarks:
    * iter 0 wall time (first-call; includes plan build + JIT)
    * cached average over iters 1..iters-1
    * cached min / max
    * speedup vs first-call

-------------------------------------------------------------------------------
 Quick demo
-------------------------------------------------------------------------------

    ./build/programming_examples/fft_universal/metal_example_fft_universal_demo

Runs a 1000-point FFT of a pure tone and prints the top magnitude bins so you
can eyeball correctness.

-------------------------------------------------------------------------------
 Compare against PyTorch
-------------------------------------------------------------------------------
fft_universal mirrors torch.fft.fft semantics (forward, un-normalised). Use
the Python script from fft/ with any N:

    python3 tt_metal/programming_examples/fft/python/compare_with_torch.py \
        --binary ./build/programming_examples/fft_universal/metal_example_fft_universal_demo \
        --N 1000

(Update the binary path to whichever example you're comparing.)

-------------------------------------------------------------------------------
 When to use which kernel
-------------------------------------------------------------------------------
    N = power of two, N <= 65,536          -> fft/            (one dispatch)
    N = power of two, 65K < N <= 1M         -> fft_stockham/   (3 dispatches)
    N = anything else, or mixed pipelines   -> fft_universal/  (this folder)
