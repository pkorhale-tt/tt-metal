================================================================================
       SCENARIO: PATH A -- batched pow2 sub-FFTs (sub_N <= 1024)
================================================================================

Path:    batched_siblings_fft(count, len)
            with len pow2, len > 32, len <= 1024
            -> ONE batch_fft(sub_N=len, batch=count) dispatch
Kernel:  batch_fft_compute  (SFPU fp32)
Cores:   min(batch_padded, 64)

This path is what makes Bluestein and Mixed-radix fast: instead of
serializing many small FFTs across cores, ONE dispatch processes all
of them in parallel.

--------------------------------------------------------------------------------
WHY BATCH MUST BE A POWER OF 2
--------------------------------------------------------------------------------

Code (fft_stockham_host.cpp:239):
    assert(is_pow2(batch) && batch >= 1);

When the caller (Bluestein, Mixed-radix) asks for an arbitrary count,
batched_siblings_fft pads count UP to the next power of 2 and adds
zero-input rows. The output for those padded rows is computed but
discarded.

--------------------------------------------------------------------------------
CORE COUNT FORMULA
--------------------------------------------------------------------------------

    sub_N = len               (must be pow2, <= 1024)
    batch = next_pow2(count)  (must be pow2, >= 1)

    num_cores      = min(batch, 64)
    batch_per_core = batch / num_cores
    grid           = pick_batch_grid(num_cores)

--------------------------------------------------------------------------------
EXAMPLE D: COUNT = 50, LEN = 256  (mixed-radix recursion, padding)
--------------------------------------------------------------------------------

  batch = next_pow2(50) = 64                  <-- padded by 14 zero rows
  num_cores      = 64
  batch_per_core = 1
  grid           = 8 x 8

  cores 0-49: real sub-FFTs (one length-256 Stockham each)
  cores 50-63: zero-input -> zero-output, discarded by caller

  Padding waste: 14/64 = 21.9% wasted compute. Worth it because the
  alternative would be 50 individual single-core dispatches.

--------------------------------------------------------------------------------
EXAMPLE E: COUNT = 256, LEN = 64  (many small-ish sub-FFTs)
--------------------------------------------------------------------------------

  batch = 256
  num_cores      = min(256, 64) = 64
  batch_per_core = 256 / 64     = 4           <-- 4 sub-FFTs per core
  grid           = 8 x 8

  core 0  -> sub-FFTs 0,1,2,3   (each: length-64 Stockham, 6 stages)
  core 1  -> sub-FFTs 4,5,6,7
  core 2  -> sub-FFTs 8,9,10,11
  ...
  core 63 -> sub-FFTs 252..255

WITHIN one core: 4 sub-FFTs run sequentially in a for-loop.
ACROSS cores: all 64 progress in parallel.

--------------------------------------------------------------------------------
EXAMPLE F: COUNT = 1024, LEN = 1024  (large per-row dispatches)
--------------------------------------------------------------------------------

This is right on the cusp; per-row Stockham (PATH B) takes over for
any LEN > 1024. PATH A handles LEN <= 1024.

  batch = 1024
  num_cores      = 64
  batch_per_core = 1024 / 64 = 16             <-- 16 sub-FFTs per core
  grid           = 8 x 8

  core 0 -> sub-FFTs 0..15
  ...
  core 63 -> sub-FFTs 1008..1023

Each core does 16 length-1024 sub-FFTs (each: 10 butterfly stages on
a fully-filled tile) sequentially.

--------------------------------------------------------------------------------
WHAT EACH ACTIVE CORE DOES
--------------------------------------------------------------------------------

For each k in [0, batch_per_core):
  reader   -> read input tile (base + k) + LOG2_SUB_N twiddle tiles
  compute  -> log2(sub_N) in-place butterfly stages   [SFPU fp32]
  writer   -> write output tile (base + k) to DRAM

Per-core-per-FFT work scales with sub_N (LOG2 stages); per-FFT
parallelism comes from the 64-way batch split.
