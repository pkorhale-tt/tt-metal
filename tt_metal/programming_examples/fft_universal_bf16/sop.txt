fft_universal_bf16 — Standard Operating Procedure
=================================================

WHAT THIS IS
------------
TRUE-bf16 sibling of fft_universal. Every multiply on the Tensix is a
bf16 × bf16 → fp32 FPU matmul. No SFPU butterflies; no "bf16 storage
with fp32 SFPU compute" trick (that is what fft_bf16/ does — and it is
why fft_bf16 is NOT true bf16 compute on this hardware).

The hardware rule we are enforcing:
  * SFPU on Wormhole has no native bf16 math. Any bf16 operand entering
    the SFPU is upcast to fp32.
  * FPU (matmul unit) has native bf16 multipliers with fp32 accumulate.
  * ∴ true bf16 compute is only reachable via matmul_tiles.
  * ∴ FFT butterflies have to be re-expressed as matmuls. That is the
    architectural thesis of this whole folder.

PHASE STATUS
------------
  Phase 1 (DONE):
      * N ∈ [2, 32]: packed direct-DFT as a complex 32×32 matmul.
        Covers all pow2, all primes, and all composites in that range
        through a single kernel trio.

  Phase 2b (DONE, this commit):
      * Generic two-level Cooley-Tukey, one function with N1 ∈ [2, 32]:
          - pow2 N > 32: N1 = 32 (pass-2 is length-32 direct DFT).
          - composite non-pow2 N > 32 with a divisor ≤ 32:
            N1 = largest_divisor_le_32(N) (pass-2 is length-N1 direct
            DFT, still in the Phase-1 kernel).
        Pass-1 recurses via the top-level fft() dispatcher, so arbitrary
        depth is handled naturally. When the sub-FFT length drops to
        ≤ 32 the recursion terminates in Phase 1.
      * The between-pass complex twiddle + transpose happens on the
        host in fp32 — pointwise ops have zero reduction depth, so
        fp32-on-host is strictly more accurate than bf16-on-device. The
        "true bf16 compute" contract applies to the reduction path
        (matmul), which stays on-device in bf16 throughout.
      * No new kernel code. All Phase 2b logic is ~150 lines of host
        orchestration in fft_universal_bf16_host.cpp.

  Phase 2c (DONE, this commit):
      * Bluestein's chirp-Z transform for:
          - prime N > 32
          - composite N > 32 with NO divisor ≤ 32 (e.g. N = 37² = 1369)
        Length-M = next_pow2(2N-1) convolution, three length-M FFTs
        (all go back through Phase 2b on bf16), chirp multiplies done
        on the host in fp32. Same discipline: reduction on device in
        bf16, pointwise on host in fp32.
      * ~90 lines of host orchestration, zero new kernels.

  COVERAGE: fft_universal_bf16::fft(md, signal) now accepts ANY N ≥ 2.
  No "not yet implemented" paths remain.

COMMON PITFALLS
---------------
1.  UnpackToDestFp32 + matmul = corrupt output.
    Do NOT set unpack_to_dest_mode on the compute kernel. That mode
    routes tiles directly to DST and leaves srcA / srcB uninitialised,
    so matmul_tiles multiplies garbage. The fp32 packed_dft kernel
    hit this bug once already; the bf16 version documents it and keeps
    matmul defaults.

2.  CB data format must match the buffer data format.
    Our DRAM MeshBuffers store bf16 bytes (2 B/elem) and our CBs are
    Float16_b. If you swap one to Float32 and forget the other, the
    NoC tile reads silently truncate / zero-extend and the kernel
    produces garbage without any runtime error.

3.  fp32_dest_acc_en is REQUIRED for multi-matmul accumulation.
    Two matmul_tiles calls share DST to form one complex output. With
    fp32_dest_acc_en=false the accumulator is bf16 and the running
    sum rounds twice, dropping SNR by ~6 dB. Keep it true.

4.  Large-N latency is dominated by dispatch count, not compute.
    Phase 2b recurses without batching same-size siblings, so N=2048
    does ~65 kernel dispatches, N=16384 does ~65, N=65536 does ~2080.
    At ~0.14 ms/dispatch warm that is visible on the wall clock. This
    is not a bug — it is correctness-first engineering. The
    "batched same-size sub-FFT kernel" optimisation in FUTURE WORK
    collapses these to 1-2 dispatches per pass.

5.  Host-side twiddle / chirp is INTENDED, not a bug.
    Between device passes (Phase 2b) and inside Bluestein (Phase 2c)
    we do the pointwise complex multiplies on the host in fp32.
    Pointwise has zero reduction depth, so fp32-on-host is strictly
    more accurate than bf16-on-device would be. The reduction path
    (matmul) is where bf16 vs fp32 actually matters — and that stays
    on the FPU in bf16 throughout.

PRECISION NOTES
---------------
Every device round-trip adds 2 bf16 roundings on the critical path
(input re-pack before the kernel, output pack after). The pointwise
host work between passes is fp32 and does NOT add a rounding until it
re-enters a bf16 CB for the next pass.

  Phase 1 (one dispatch)              : 2 bf16 roundings → SNR 48-56 dB
  Phase 2b pow2 depth-1 (≤ 1024)      : 4 bf16 roundings → SNR 46-50 dB
  Phase 2b pow2 depth-2 (≤ 32768)     : 6 bf16 roundings → SNR 40-46 dB
  Phase 2b pow2 depth-3 (≤ 1048576)   : 8 bf16 roundings → SNR 36-42 dB
  Phase 2b mixed-radix                : depth-dependent (2 to 6 roundings)
  Phase 2c Bluestein                  : 3 × (depth of length-M pow2 FFT)
                                        e.g. prime 1009 → M=2048 depth-2
                                        → 3 × 6 = 18 bf16 roundings
                                        → SNR ~34-38 dB

These numbers are the inherent bf16 floor for a FPU-matmul FFT at the
given recursion depth. No amount of kernel tuning will improve them —
tightening SNR requires either fewer recursion levels (better kernel
batching, FUTURE WORK) or fp32 (fft_universal/).

DEBUGGING TIPS
--------------
  * Run the demo at a single bin first — expected output is a clean
    spike of magnitude N at bin k_in. If you see spikes at multiple
    bins or a flat response, the tilize / untilize path is broken.
  * Random-input rel_err > 1e-2 at small N suggests either the
    UnpackToDestFp32 trap (see above) or a CB-format mismatch.
  * If the build compiles but crashes inside mm_init, check that CBs
    0 / 1 / 2 / 3 are all Float16_b and all have the same 2048 B tile
    size. mm_init infers srcA / srcB format from whichever CB you hand
    it — mixing formats is a runtime bug, not a compile-time one.

FUTURE WORK
-----------
Coverage is now complete for all N ≥ 2. Remaining work is performance.
See README.md § "Roadmap" for the full list. Short version:

  1. Batched same-size sub-FFT kernel. Today pass-1 of a pow2 N ∈
     [2048, 32768] issues 32 separate dispatches for the length-(N/32)
     sub-FFTs. A kernel that takes a `count > 32` parameter — i.e.
     many packed-DFT tiles in flight at once — would collapse each
     pass to one dispatch and give us 30-60× throughput on large N.

  2. Device-side twiddle + transpose kernel using mul_tiles +
     add_tiles / sub_tiles on bf16 CBs (still FPU, still true bf16).
     Removes the PCIe bounce between passes. Accuracy cost for bf16
     pointwise is bounded because pointwise has zero reduction depth.

  3. Multi-core sharding. packed_dft_bf16 currently runs on a single
     Tensix; sharding `count` siblings across cores gives near-linear
     wall-clock improvement on the dispatches where count is large.

  4. FFT of length 2^k for large k (e.g. 2^20) via a dedicated
     Stockham-style kernel instead of recursion. Our recursive path
     does this correctly today but is bandwidth-bound.
