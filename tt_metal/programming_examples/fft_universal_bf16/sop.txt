fft_universal_bf16 — Standard Operating Procedure
=================================================

WHAT THIS IS
------------
TRUE-bf16 sibling of fft_universal. Every multiply on the Tensix is a
bf16 × bf16 → fp32 FPU matmul. No SFPU butterflies; no "bf16 storage
with fp32 SFPU compute" trick (that is what fft_bf16/ does — and it is
why fft_bf16 is NOT true bf16 compute on this hardware).

The hardware rule we are enforcing:
  * SFPU on Wormhole has no native bf16 math. Any bf16 operand entering
    the SFPU is upcast to fp32.
  * FPU (matmul unit) has native bf16 multipliers with fp32 accumulate.
  * ∴ true bf16 compute is only reachable via matmul_tiles.
  * ∴ FFT butterflies have to be re-expressed as matmuls. That is the
    architectural thesis of this whole folder.

PHASE STATUS
------------
  Phase 1 (DONE):
      * N ∈ [2, 32]: packed direct-DFT as a complex 32×32 matmul.
        Covers all pow2, all primes, and all composites in that range
        through a single kernel trio.

  Phase 2a (DONE, this commit):
      * pow2 N ∈ [64, 1024]: two-level Cooley-Tukey with N = 32 × N2,
        N2 ∈ {2, 4, 8, 16, 32}. Reuses the Phase-1 kernel for BOTH
        passes (pass-1 = 32 sibling length-N2 DFTs, pass-2 = N2 sibling
        length-32 DFTs). The pointwise complex twiddle between passes
        happens on the host in fp32 — pointwise is a no-reduction op, so
        fp32-on-host is strictly more accurate than bf16-on-device and
        does NOT violate the "true bf16 compute" contract. The contract
        is about the reduction path (matmul), which stays on-device in
        bf16 for both passes.
      * No new kernel code. ~100 lines of host orchestration.
      * Test binary now covers pow2 N ∈ {64, 128, 256, 512, 1024};
        benchmark and demo accept those sizes too.

  Phase 2b (PENDING):
      * pow2 N > 1024. Two paths to explore:
          - recurse via Phase 2a (e.g. N = 32³ = 32768 splits as
            32 × 1024 and delegates pass-2 to Phase 2a);
          - introduce a device-side twiddle+transpose kernel using
            mul_tiles / add_tiles / sub_tiles on bf16 CBs (still FPU,
            still true bf16 — SFPU never touched). Avoids PCIe bounce
            between passes, required once N is big enough that the host
            round trip dominates.

  Phase 2c (PENDING):
      * prime N > 32 (Bluestein) and composite non-pow2 N (mixed-radix
        Cooley-Tukey). Both ultimately invoke a pow2 FFT, so once Phase
        2b lands these are host-only glue.

COMMON PITFALLS
---------------
1.  UnpackToDestFp32 + matmul = corrupt output.
    Do NOT set unpack_to_dest_mode on the compute kernel. That mode
    routes tiles directly to DST and leaves srcA / srcB uninitialised,
    so matmul_tiles multiplies garbage. The fp32 packed_dft kernel
    hit this bug once already; the bf16 version documents it and keeps
    matmul defaults.

2.  CB data format must match the buffer data format.
    Our DRAM MeshBuffers store bf16 bytes (2 B/elem) and our CBs are
    Float16_b. If you swap one to Float32 and forget the other, the
    NoC tile reads silently truncate / zero-extend and the kernel
    produces garbage without any runtime error.

3.  fp32_dest_acc_en is REQUIRED for multi-matmul accumulation.
    Two matmul_tiles calls share DST to form one complex output. With
    fp32_dest_acc_en=false the accumulator is bf16 and the running
    sum rounds twice, dropping SNR by ~6 dB. Keep it true.

4.  N not in [2, 32] ∪ pow2-[64, 1024] does not fall back — it throws.
    Intentional. If you need an unsupported N today, use fft_universal/
    (fp32). Once Phase 2b/2c land, the same API will cover all N.

5.  Phase 2a: host-side twiddle is INTENDED, not a bug.
    Between the two device passes we do the pointwise complex twiddle
    on the host in fp32. Pointwise is a no-reduction op, so fp32 there
    is strictly more accurate than bf16. The reduction path (matmul)
    is where bf16 vs fp32 actually matters — and that stays on the FPU.
    Phase 2b moves the twiddle onto the device too so we can hide the
    PCIe round trip; until then the ~microsecond bounce is fine for
    N ≤ 1024.

PRECISION NOTES
---------------
Phase 1 (single pass):
  * Per-multiply rounding: 1 bf16 × bf16 product → fp32 (exact in fp32).
  * Per-accumulate: fp32 running sum. No rounding on the inner dot.
  * Per output tile: ONE fp32 → bf16 pack at pack_tile().
  * Total bf16 roundings on the critical path = 2 (input pack + output
    pack) for any N ≤ 32. SNR holds at ~44-55 dB across the phase.

Phase 2a (two passes + host twiddle):
  * Each pass: same 2 bf16 roundings as Phase 1.
  * Host twiddle: fp32 pointwise (no additional bf16 rounding until the
    bf16 re-pack entering pass-2).
  * Total bf16 roundings on the critical path = ~4 (input pack, pass-1
    output pack, pass-2 input pack, pass-2 output pack). SNR drops by
    ~3-6 dB vs Phase 1 — empirically 38-45 dB on random input.

DEBUGGING TIPS
--------------
  * Run the demo at a single bin first — expected output is a clean
    spike of magnitude N at bin k_in. If you see spikes at multiple
    bins or a flat response, the tilize / untilize path is broken.
  * Random-input rel_err > 1e-2 at small N suggests either the
    UnpackToDestFp32 trap (see above) or a CB-format mismatch.
  * If the build compiles but crashes inside mm_init, check that CBs
    0 / 1 / 2 / 3 are all Float16_b and all have the same 2048 B tile
    size. mm_init infers srcA / srcB format from whichever CB you hand
    it — mixing formats is a runtime bug, not a compile-time one.
