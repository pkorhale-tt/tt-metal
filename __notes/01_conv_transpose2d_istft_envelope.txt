================================================================================
  SECTION 1 — TEST PARAMETERS DEMYSTIFIED
================================================================================

  pytest.param(1, 1, 640, 160, 96, False, id="istft_envelope")
                |  |  |    |    |   |
                |  |  |    |    |   +-- with_bias        = False
                |  |  |    |    +------ T (input frames) = 96
                |  |  |    +----------- stride           = 160   (hop length)
                |  |  +---------------- kernel_size      = 640   (n_fft)
                |  +------------------- out_channels     = 1
                +---------------------- in_channels      = 1

  WHY in=1, out=1?
  ----------------
  Real iSTFT does:
       envelope[n] = sum over k of  w[n - k*hop]^2          (window overlap-add)
       y[n]        = ifft_overlap_add(spectrum) / envelope[n]

  The "envelope" is a single 1-D tensor (no spectral content), so it is
  computed by passing an all-ones (or window-squared) signal through the
  same ConvTranspose1d that does overlap-add. Hence channels = 1.

  SECTION 2 — PYTORCH REFERENCE SHAPES
================================================================================

  weight = randn(in=1, out=1, K=640)
  x_pt   = randn(N=1, C_in=1, T=96)
  ref    = F.conv_transpose1d(x_pt, weight, stride=160)

  Output length formula for ConvTranspose1d:
        T_out = (T - 1)*stride - 2*padding + dilation*(K - 1) + output_pad + 1
              = (96 - 1)*160 - 0 + 1*(640 - 1) + 0 + 1
              = 15200 + 639 + 1
              = 15840

  ref.shape == [1, 1, 15840]


================================================================================
  SECTION 3 — RESHAPING 1D INTO TTNN'S 2D API (H = 1)
================================================================================

  ttnn.conv_transpose2d expects NHWC input and a 2D kernel.
  We collapse one spatial dim by setting H=1.

         x_pt    [B=1, C=1, T=96]        (NCT)
            |
            | transpose(1,2)               -> [1, 96, 1]   (NTC)
            | unsqueeze(1)                 -> [1, 1, 96, 1] (NHWC, H=1, W=T)
            v
         x_nhwc  [B=1, H=1, W=96, C_in=1]

         weight  [in=1, out=1, K=640]
            |
            | unsqueeze(2)                 -> [1, 1, 1, 640]
            v                                  (in, out, K_h=1, K_w=K)

  So inside the device the conv sees:
        Input:   [B=1, H=1, W=96, C_in=1]
        Weight:  [in=1, out=1, K_h=1, K_w=640]
        Stride:  (1, 160)
        Padding: (0, 0)


================================================================================
  SECTION 4 — INSIDE ttnn.conv_transpose2d
================================================================================

  File: ttnn/cpp/ttnn/operations/conv/conv_transpose2d/conv_transpose2d.cpp

  The L1 path executes these stages:

     ttnn.conv_transpose2d(...)
            |
            v
     [A] compute_conv_transpose2d_dimensions(...)
            |       (figures out output_h/w, full_input_h/w,
            |        strided_input_h/w, real padding L/R/T/B)
            v
     [B] determine_conv_config_for_auto_shard(...)
            |       (picks HEIGHT/BLOCK/WIDTH sharding,
            |        decides num_cores_nhw, num_cores_c)
            v
     [C] shard_or_reshard_tensor_if_required(...)
            |       (re-shards the DRAM input into L1 sharded tensor)
            v
     [D] transform_weights_for_conv_transpose2d(weight, mirror_kernel=True)
            |       (kernel flip + IOHW -> OIHW layout for conv2d)
            v
     [E] sliding_window_config = SlidingWindowConfig{ ..., is_transpose = true };
            |
            v
     [F] halo_output = ttnn::halo(input_tensor_post_tm, sliding_window_config);
            |       (HERE the magic happens: untilize + zero-interleave + pad +
            |        gather neighbor sticks across cores)
            v
     [G] output = ttnn::prim::conv2d(
                      halo_output,
                      weight,
                      stride={1,1}, padding=0,        <-- always for transpose
                      sliding_window_config, ...);
            |
            v
     OUTPUT (sharded across cores)


================================================================================
  SECTION 5 — HOW H AND W (output) ARE COMPUTED
================================================================================

  In SlidingWindowConfig::get_output_shape() (sliding_window.cpp:62):

      if (is_transpose) {
          output_h = (input_h - 1)*stride_h - get_pad_h() +
                     dilation_h*(K_h - 1) + output_pad_h + 1
          output_w = (input_w - 1)*stride_w - get_pad_w() +
                     dilation_w*(K_w - 1) + output_pad_w + 1
      }

  Plug in our values:

      output_h = (1  - 1)*1   - 0 + 1*(1   - 1) + 0 + 1 = 1
      output_w = (96 - 1)*160 - 0 + 1*(640 - 1) + 0 + 1 = 15840

  The "full input" size that halo must materialize for conv2d to consume:

      full_input_h = output_h + dilation_h*(K_h - 1) = 1     + 0   = 1
      full_input_w = output_w + dilation_w*(K_w - 1) = 15840 + 639 = 16479

  Real padding around the strided input (get_transposed_real_padding):

      strided_input_h = (input_h - 1)*stride_h + 1 = 1
      strided_input_w = (input_w - 1)*stride_w + 1 = (96-1)*160 + 1 = 15201

      base_pad_h = dilation_h*(K_h - 1) = 0
      base_pad_w = dilation_w*(K_w - 1) = 639

      input_pad_left = input_pad_right = base_pad_w / 2  = 319 / 320  (split)
      Actually: input_pad_left/right depends on user-supplied padding;
                with padding=0, both sides receive (base_pad_w) bytes total.
                In code the split = base_pad_w around the strided input.

  Important geometric fact:

      full_input_w = strided_input_w + input_pad_left + input_pad_right
      16479        = 15201           + 1278   (split as 639 + 639)


================================================================================
  SECTION 6 — WHAT HALO ACTUALLY DOES (deep)
================================================================================

  Halo is one device op (UntilizeWithHaloProgramFactory) that does THREE jobs
  in a single sweep:

      (1) UNTILIZE  : convert TILE -> ROW_MAJOR (sliding-window addressing
                      is row-by-row).
      (2) PAD       : write `pad_val` (=0) at every position marked as padding.
      (3) HALO GATHER: each core pulls neighbor "sticks" (a stick = one
                      C-vector at one (h,w)) into its own L1 so that the
                      conv kernel's window never has to cross core boundaries.

  Where does halo know what is "pad" vs "real"?
  ---------------------------------------------
  Host code generates 3 metadata tables BEFORE halo runs:

      generate_pad_metadata(config)   -> bool[]   (pad? per (h,w) of full input)
      generate_op_trace_metadata(cfg) -> uint32[] (for each output stick:
                                                   which input stick to read)
      generate_shard_boundaries(cfg)  -> per-core (start, end) ranges

  For is_transpose = true, generate_pad_metadata marks BOTH:
      a) outer pad ring   (h < pad_top, etc.)
      b) interleaved zeros: positions where (h - pad_top) % stride_h != 0
                            OR    where (w - pad_left) % stride_w != 0

  That second rule is the trick: halo does the "stride > 1 upsample with
  interleaved zeros" by simply marking those cells as PADDING. The
  downstream conv2d then reads them as legitimate zero values.

  For our case:
      full_input_w  = 16479
      strided_input = 15201   (only 1 in every 160 positions is "real")
      96 real values lie at positions:  639, 799, 959, ..., 639 + 95*160 = 15839

  After halo (per-core view of the 16479-stick row):

      .  .  .  .  R  .  .  .  .  R  .  .  .  .  R  .  .   (R = real, . = zero)
      <-- 639 -->  <-- 159 -->    <-- 159 -->


================================================================================
  SECTION 7 — AUTO-SHARDER PICKS 62 CORES (HEIGHT_SHARDED)
================================================================================

  Conv2dConfig.shard_layout = None  (not specified)

  -> determine_conv_config_for_auto_shard tries HEIGHT, BLOCK, WIDTH and
     picks the one with smallest L1 footprint per core.

  HEIGHT_SHARDED math (which wins for this skinny tensor):

      out_nhw_ntiles      = ceil(B*H_out*W_out / TILE_HEIGHT)
                          = ceil(1*1*15840 / 32) = 495
      act_block_h_ntiles  = act_block_h_override / TILE_HEIGHT = 32/32 = 1
      max_num_cores       = 64                  (Wormhole 8x8)

  find_closest_largest_divisor_with_num_padding_and_mult(495, 64, 1):

      div=64: padded = round_up(495, 64*1) = 512   waste = 17 ;
              17 >= 512/64 = 8   -> shrink
      div=63: padded = round_up(495, 63*1) = 504   waste = 9  ;
               9 >= 504/63 = 8   -> shrink
      div=62: padded = round_up(495, 62*1) = 496   waste = 1  ;
               1 <  496/62 = 8   -> STOP, return 62

  Therefore:
      num_cores_nhw = 62
      per-core output sticks = 8 tiles * 32 = 256
      total padded output    = 62 * 256 = 15872  (32 sticks of edge padding)

================================================================================
  SECTION 9 — DATA-PER-CORE *BEFORE* HALO  (input has only 96 real sticks)
================================================================================

  Input tensor: [B=1, H=1, W=96, C_in=1]    (96 sticks total)

  determine_input_memory_config:
      nhw_padded  = round_up(96, 62 * TILE_HEIGHT)
                  = round_up(96, 62 * 32)
                  = round_up(96, 1984) = 1984
      shard_height_per_core = 1984 / 62 = 32 sticks

  So each core gets 32 sticks. Real values fill the first 96 sticks (= 3 cores
  worth). The rest are zero padding.

      Core   range of stick indices    real sticks   zero pad
      ------+---------------------+--+-----------+-------------
      C0     [  0 ..  31]              32           0
      C1     [ 32 ..  63]              32           0
      C2     [ 64 ..  95]              32           0
      C3     [ 96 .. 127]               0          32
      C4     [128 .. 159]               0          32
      ...                              ...         ...
      C61    [...      ]                0          32

  Visualization (each cell = 32-stick shard on one core):

      C0  C1  C2  C3  C4  C5  C6 ... C61
     [RR][RR][RR][..][..][..][..]...[..]
       ^^^^^^^^^^^
       only these 3 cores hold real data


================================================================================
  SECTION 10 — DATA-PER-CORE *AFTER* HALO  (zero-interleaved, 16479 sticks)
================================================================================

  After halo:
      Effective row length = full_input_w = 16479 sticks
      Distributed across the same 62 cores
      Per-core shard = ceil(16479 / 62) ~ 266 "owned" sticks
                       PLUS halo overlap of (K_w - 1) = 639 sticks for the
                       conv2d window.

      So each core's halo-output L1 holds approximately:
          owned + halo = 266 + 639 = 905 sticks (ROW_MAJOR, fp32, C=1)

  Real values in the 16479-buffer sit at positions 639, 799, 959, ..., 15839
  (96 positions in total, spaced by stride=160).

  A simplified slice of the per-core distribution (real values per core):

      Core    halo input range         # real values
      -------+----------------------+--+--------------
      C0      [    0 ..    904]         2   (positions 639, 799)
      C1      [  266 ..   1170]         5   (positions 639,799,959,1119)
      C2      [  532 ..   1436]         5
      C3      [  798 ..   1702]         6
      C4      [ 1064 ..   1968]         6
      ...
      C61     [15574 ..  16478]         2   (positions 15679, 15839)

  In all cases, the OVERWHELMING majority of each core's 905 sticks are zeros
  (interleaved or outer pad), with only ~2-6 real values scattered in.

  ASCII picture of one core's halo shard (zoomed):

      ................R...............R................R...............
      |<----- ~159 zeros ----->|<----- ~159 zeros ----->|
        (R = real value coming from x_pt[i] for some i)


================================================================================
  SECTION 11 — HOW EACH CORE COMPUTES ITS 256 OUTPUT STICKS
================================================================================

  Each output core runs the SAME conv2d body locally:

       for j = 0 .. 255:                       # 256 output sticks per core
           acc = 0
           for k = 0 .. 639:                   # K_w sweep
               acc += halo_local[j + k] * weight[k]
           output_local[j] = acc + bias        # bias = 0 (with_bias=False)

  Per core:
      MACs               = 256 * 640 = 163,840
      Reads (real data)  = 256 + 639 = 895 sticks (from local L1)
      Writes             = 256 sticks
      No NoC reads during compute (halo already moved everything in)

  Compute is fully data-parallel across 62 cores.

  ASCII of one output stick computation:

         halo shard on core (905 sticks):
         [ ... s_j  s_j+1  s_j+2  ...  s_j+639 ... ]
                |     |       |             |
                v     v       v             v
              w[0]  w[1]    w[2]   ...    w[639]
                \____|_______|_____ ... ___/
                     +-> sum -> output[j]

================================================================================
  SECTION 13 — WHY THIS CASE FAILS (currently)
================================================================================

  The conv2d *reader kernel* on each Tensix wants to do ONE coalesced NoC read
  for an entire activation row of the kernel window.

      coalesced_read_bytes ~= K_w * in_channels_padded * dtype_size

  For our case:
      K_w                   = 640
      in_channels_padded    = 16    (alignment for 1-channel fp32 inputs)
      dtype_size            = 4     (fp32)

      coalesced_read_bytes ~= 640 * 16 * 4 = 40,960 bytes

  Wormhole NoC max single-burst size:
      NOC_MAX_BURST_SIZE   = 8,192 bytes (8 KB)

  In the reader kernel:

      static_assert(coalesced_read_bytes <= NOC_MAX_BURST_SIZE,
                    "coalesced read exceeds NoC burst limit");

  -> Compile-time failure for K_w = 640 with C_in = 1 fp32.

  This is why the test docstring marks the istft cases as known-failing
  ("xfail until ttnn.conv_transpose2d supports very large kernel widths").

  The math itself is correct -- if the kernel could be split into smaller
  reads, you'd get PCC ~ 1.0 vs PyTorch.
