================================================================================
  CHAPTER 1 - THE PERFORMANCE MODEL  (predict any shape)
================================================================================

  ----------------------------------------------------------------------
  KEY QUANTITIES
  ----------------------------------------------------------------------

  Let:
      C_in    = input channels
      C_out   = output channels
      K       = kernel width (W axis; H=1 for 1D-as-2D)
      S       = stride along W
      T       = input length (W)
      T_out   = (T-1)*S + K       (output length)

  ----------------------------------------------------------------------
  MAC COUNT (the inner work)
  ----------------------------------------------------------------------

  Current approach (halo + conv2d):
      total_MACs = T_out * K * C_in * C_out

  Polyphase approach:
      K_p = ceil(K / S)
      T_per_phase = ceil(T_out / S)
      MACs_per_phase = T_per_phase * K_p * C_in * C_out
      total_MACs = S * MACs_per_phase

  Polyphase savings ratio:
      current  /  polyphase
        ~= (T_out * K)  /  (S * T_per_phase * K_p)
        ~= (T_out * K)  /  (T_out * K_p)
        ~= K / K_p
        ~= S    (when K_p ~ K/S)

  So the asymptotic MAC speedup is approximately S (the stride).

  ----------------------------------------------------------------------
  NoC TRAFFIC (the data movement)
  ----------------------------------------------------------------------

  Current approach reads K_w * in_ch_padded * dtype bytes per coalesced
  burst, S+1 times more bursts than needed (because of zero positions).

  Polyphase reads (K_w / S) * in_ch_padded * dtype bytes per burst.
  Bursts are smaller AND there are fewer wasted ones.

  NoC traffic ratio:  approximately S
                      (matches the MAC ratio).

  ----------------------------------------------------------------------
  END-TO-END SPEEDUP (estimate)
  ----------------------------------------------------------------------

  In real ops, time decomposes as:
      total_time  =  setup + halo + compute + writeback
                   ~ setup + (halo + compute) * (proportional to MACs)

  For shapes that are MAC-bound (most large convs), end-to-end speedup
  tracks MAC speedup: roughly S.

  For shapes that are LAUNCH-bound (very small kernels), end-to-end
  speedup is smaller because launch overhead does not scale with MACs.

  For iSTFT envelope specifically: end-to-end speedup ~100-200x because
  current path doesn't compile at all -- so "infinitely faster" with a
  conservative number applied for clarity.

================================================================================
  CHAPTER 3 - END-TO-END MODEL SPEEDUPS
================================================================================

  Estimated improvement when polyphase is enabled, measured in the
  total inference latency of an entire model that contains
  conv_transpose2d layers.

  ----------------------------------------------------------------------
  Model: TtIstft (your immediate use case)
  ----------------------------------------------------------------------
      Per call uses:
          - 1x istft_envelope (C_in=1, C_out=1, K=640, S=160)
          - 2x istft_cos_or_sin (C_in=321, C_out=1, K=640, S=160)

      Current status:
          conv_transpose2d NEVER RUNS -- you fall back to CPU iSTFT
          or skip the operation entirely.

      With polyphase:
          All 3 calls run natively on TT.
          End-to-end TtIstft latency: drops from "CPU fallback" to
          comfortably real-time (<1 ms per inference for typical
          frame counts).

      Expected speedup:    INFINITE (was not on accelerator at all)
                           or 30-100x vs CPU iSTFT in absolute terms.

  ----------------------------------------------------------------------
  Model: HiFi-GAN-style vocoder
  ----------------------------------------------------------------------
      Has 4 transpose conv layers with stride 8, 8, 2, 2 and modest
      channel counts.

      Two layers (stride 8) get ~7-8x each.
      Two layers (stride 2) get ~1.5-2x each (detector may or may not
      fire depending on tuning).

      Mix of work share roughly 50/50 between strides.

      Expected end-to-end model speedup: ~3-4x.

  ----------------------------------------------------------------------
  Model: U-Net image segmentation
  ----------------------------------------------------------------------
      All transpose layers use stride 2 with hundreds of channels.
      Detector does NOT fire (channels too large, savings too small).

      Expected end-to-end speedup:    1.0x (no change, no regression).

      This is the desired behavior -- we don't want to hurt models
      that already work well.


================================================================================
  CHAPTER 4 - LATENCY BREAKDOWN CHANGES
================================================================================

  How does each stage's cost change?

  +-------------------------+-----------------+------------------+-----------+
  | Stage                   | Current (us)    | Polyphase (us)   | Notes     |
  |                         | (iSTFT envelope)|                  |           |
  +-------------------------+-----------------+------------------+-----------+
  | Host: dimension compute | ~5              | ~5               | identical |
  | Host: weight prep       | ~50 (mirror)    | ~80 (mirror+     | one-time  |
  |                         |                 |   shuffle)       | per layer |
  | Host: shard config      | ~30             | ~30              | identical |
  | Device: shard tensor    | ~20             | ~20              | identical |
  | Device: halo            | ~200 (huge      | ~5 (only pad)    | 40x       |
  |                         |  zero buffer)   |                  | smaller   |
  | Device: conv2d          | DOES NOT RUN    | ~80 (S small     |           |
  |                         |  (compile fail) |  conv2ds)        |           |
  | Device: interleave      | NA              | ~10              | new step  |
  | Total per call          | INF (fails)     | ~230 us          |           |
  +-------------------------+-----------------+------------------+-----------+

  Notes:
      - Weight prep is a one-time cost per model load. Cache it (note 07
        item 7.1) and it disappears from per-call latency.
      - Halo cost drops by ~40x because the zero-interleaved buffer is
        eliminated -- only a small ttnn::pad of length ~3 zeros runs.
      - The S separate conv2d launches add some host overhead. The
        grouped-conv batching optimization (notes 08 Chapter 8) brings
        this down further once implemented.


================================================================================
  CHAPTER 5 - MEMORY AND L1 / DRAM BANDWIDTH CHANGES
================================================================================

  ----------------------------------------------------------------------
  L1 footprint per core (during conv_transpose2d run)
  ----------------------------------------------------------------------
                                Current             Polyphase
      Activation buffer:        ~5 KB (mostly       ~50 bytes per phase,
                                zeros from halo)    summed over phases
      Halo gather config:       ~1 KB               0 (no halo)
      Weight cache:             same                same (slightly larger
                                                    because S phases)
      Output buffer:            same                same (final output
                                                    matches)
      -----                     ----                ----
      Peak L1 use (iSTFT):      ~8 KB / core        ~3 KB / core
                                                    (>2x more headroom
                                                     for next op)

  ----------------------------------------------------------------------
  DRAM bandwidth (the input + weight reads + output writes)
  ----------------------------------------------------------------------
                                Current             Polyphase
      Input read:               T * C * dt          T * C * dt
                                = 96 * 1 * 4        = 96 * 1 * 4
                                = 384 bytes         = 384 bytes
      Weight read:              K * dt              K * dt
                                = 2.56 KB           = 2.56 KB (same total,
                                                       rearranged)
      Output write:             T_out * dt          T_out * dt
                                = 15.5 KB           = 15.5 KB

  TL;DR: DRAM bandwidth identical (we read/write the same amount of
  real data). The big savings are in L1 + NoC, not DRAM.

  ----------------------------------------------------------------------
  Peak L1 reduction enables larger BATCH sizes
  ----------------------------------------------------------------------
  Since each core uses ~2x less L1, models that previously OOM'd on L1
  can run with larger batches under polyphase.


================================================================================
  CHAPTER 6 - NoC TRAFFIC CHANGES
================================================================================

  ----------------------------------------------------------------------
  Total NoC bytes per call (iSTFT envelope, 62 cores)
  ----------------------------------------------------------------------
      Current path:
          Halo gather:        62 cores * ~5 KB shard transfer = ~310 KB
          Conv2d reader:      62 cores * 256 outputs * 40,960 byte burst
                                                            = ~650 MB
                              (but the kernel never compiles, so 0
                              actually moves. With auto-split-bursts
                              fix this would become real traffic.)

      Polyphase path:
          Halo gather:        0 (no halo)
          Conv2d reader:      62 cores * 256 outputs * S phases * 256 byte burst
                                                            = ~4 MB
                              (160x smaller per-burst, but S phases each)

      Net reduction: ~160x. AND the bursts now individually fit within
      NOC_MAX_BURST_SIZE -- no compile-time failure.

  ----------------------------------------------------------------------
  NoC packets per call
  ----------------------------------------------------------------------
      Current:    ~1M packets attempted (would be -- doesn't actually run)
      Polyphase:  ~250K packets (S * fewer per phase but S phases)

      Mild reduction in packet count; HUGE reduction in bytes-per-packet.


================================================================================
  CHAPTER 7 - COMPILE TIME IMPACT  (yes, this matters)
================================================================================

  Polyphase issues S separate conv2d kernels. Each is a separate
  compiled program in the runtime cache.

      Without program cache:    S * compile_time(conv2d)
                                = 160 * ~100 ms
                                = 16 seconds per layer (!)
                                BAD on first run.

      With program cache (default in ttnn):
                                S programs compiled ONCE per (shape, layout)
                                = 16 seconds first call,
                                  microseconds afterwards.

      With grouped-conv batching (notes 08 Ch 8 optimization):
                                1 program, compiled ONCE
                                = ~100 ms first call,
                                  microseconds afterwards.

  Recommendation: ship V1 with the program cache (fine for repeated
  inference), then upgrade to grouped batching in V2 for low first-call
  latency.


================================================================================
  CHAPTER 8 - SHAPES THAT DON'T BENEFIT  (where to disable polyphase)
================================================================================

  These are the cases where the existing halo + conv2d path is already
  efficient OR where polyphase would be slower:

      (a) Stride = 1:
          No zero-interleaving happens. Halo is just normal padding.
          Polyphase has nothing to optimize.
          DETECTOR returns FALSE.

      (b) Large channels (C_in > 32):
          MAC count is dominated by channels, not by K_w. The waste
          ratio (K/K_p = S) becomes a small fraction of total work.
          Net perf change is < 10%, and the extra launches hurt.
          DETECTOR returns FALSE.

      (c) Small kernel relative to stride (K < 4*S):
          K_p = ceil(K/S) is too small. Per-phase conv2ds are too tiny;
          launch overhead dominates.
          DETECTOR returns FALSE.

      (d) Tiny output (T_out < 16*S):
          The S sub-convs each have very few outputs (T_per_phase < 16).
          Hardware tile utilization is bad.
          DETECTOR returns FALSE.

      (e) H > 1 with K_h > 1 (true 2D):
          V1 of polyphase only handles 1D-as-2D (H=1, K_h=1).
          V2 generalizes; until then, V1 detector returns FALSE.

  Together these rules keep polyphase invisible for ~90% of existing
  callsites and only active for the cases that actually benefit.

  CHAPTER 9 - MEASUREMENT PLAN
================================================================================

  Before publishing the perf numbers, collect:

  ----------------------------------------------------------------------
  Microbenchmarks (the test fixtures should accept --benchmark)
  ----------------------------------------------------------------------
      1. Per-shape latency for the 8 shapes in Chapter 2.
         Use ttnn.tracer to measure setup + halo + conv + interleave
         separately.
      2. Repeat with batch_size = 1, 4, 16, 64.
      3. Repeat with fp32, bf16, bfp8.
      4. Compare polyphase ON vs OFF (env var) on the SAME hardware.

  ----------------------------------------------------------------------
  Real model benchmarks
  ----------------------------------------------------------------------
      1. TtIstft full pipeline end-to-end (the one your test exercises).
         Measure tokens/sec or samples/sec.
      2. HiFi-GAN inference end-to-end.
      3. U-Net (Vanilla & VGG) on a 512x512 image. Should be no change.

  ----------------------------------------------------------------------
  Validation alongside perf
  ----------------------------------------------------------------------
      For each measurement, also compute PCC against PyTorch reference.
      Polyphase is only "faster" if the output is still correct.
      PCC > 0.999 for fp32, > 0.99 for bf16.

  ----------------------------------------------------------------------
  Reporting template
  ----------------------------------------------------------------------
      For each shape:
          Latency (us)    : current  |  polyphase  |  speedup
          MACs            : current  |  polyphase  |  ratio
          NoC bytes       : current  |  polyphase  |  ratio
          Peak L1 (KB)    : current  |  polyphase
          PCC             : current  |  polyphase
          Notes           : detector fires? grouped batching used?
                            dtype? batch size?

================================================================================
  CHAPTER 11 - TL;DR
================================================================================

  - iSTFT shapes: goes from NEVER RUNS to comfortably real-time.
    Wall-clock improvement is INFINITE (was 0). Conservatively ~100-200x.
  - Vocoder-style shapes (medium stride, modest channels): ~5-10x
    end-to-end speedup.
  - U-Net / vision shapes: NO CHANGE (detector blocks polyphase).
    Existing high-quality path remains.
  - L1 peak usage drops ~2x for friendly shapes -> can fit larger
    batches.
  - NoC traffic drops ~100x for friendly shapes -> better network
    utilization for surrounding ops too.
  - Compile time is a CONCERN until grouped-conv batching ships
    (V2 optimization). Use program cache to hide it for repeated
    inference.

  Bottom line: polyphase is a Pareto improvement. It either makes
  things dramatically better or it does nothing -- there is no regime
  where it makes things measurably worse (assuming the detector is
  tuned conservatively).
