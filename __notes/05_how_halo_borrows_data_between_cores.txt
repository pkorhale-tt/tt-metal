================================================================================
  HOW HALO BORROWS DATA FROM ONE CORE TO ANOTHER
  (e.g. how Core 1 hands its boundary stick to Core 0)
  Verified against ttnn/cpp/ttnn/operations/sliding_window/halo/device/
                   kernels/dataflow/halo_gather.cpp
================================================================================

  The most surprising thing first:

      It is NOT "Core 0 pulls data from Core 1."
      It IS  "Core 1 PUSHES its data into Core 0's L1."

  Halo uses a PUSH model with `noc_async_write`. Senders write directly
  into receivers' L1 SRAM. The receiver never issues a read for its
  halo data. We will prove this with the actual source code.


================================================================================
  CHAPTER 1 — THE MENTAL PICTURE
================================================================================

  Imagine two neighboring cores, each with their own L1:

       +----------- Core 0 ----------+    +----------- Core 1 ----------+
       |  L1 input (own sticks):     |    |  L1 input (own sticks):     |
       |  [s0, s1, s2, s3]           |    |  [s4, s5, s6, s7]           |
       |                             |    |                             |
       |  L1 output (halo'd, empty): |    |  L1 output (halo'd, empty): |
       |  [ ?,  ?,  ?,  ?,  ?,  ?]  |    |  [ ?,  ?,  ?,  ?,  ?,  ?]  |
       +-----------------------------+    +-----------------------------+

  After halo runs:

       Core 0 output ends up with Core 0's own sticks AND its right
       neighbor's left-edge sticks (the halo from Core 1).
       Same for Core 1 (gets halo from Core 0, plus its own).

  How does that data get there? Three mechanisms work in parallel:

       (A) PADDING:   write zeros into the slots that should be pad.
                      Source = a special always-zero region of L1
                      (MEM_ZEROS_BASE).

       (B) LOCAL:     copy own sticks from own L1 input to own L1 output.
                      Source and destination are on the SAME core.

       (C) REMOTE:    push own sticks into the L1 output of a NEIGHBOR
                      core. This is the "borrowing" mechanism.

  Each core does ALL THREE in one kernel call. The host pre-computes
  exactly which transfers go where.


================================================================================
  CHAPTER 2 — PUSH vs PULL (and why ttnn picks PUSH)
================================================================================

  In principle there are two ways to move data between cores:

      PULL (remote_read=true):
          Core 0 issues `noc_async_read` to read from Core 1's L1.
          The read transaction routes Core 0 -> Core 1 (request)
          then Core 1 -> Core 0 (response).

      PUSH (remote_read=false):  <-- DEFAULT, the only one supported here
          Core 1 issues `noc_async_write` to write directly into
          Core 0's L1. One-way traffic.

  Proof from halo_gather.cpp line 258:

      static_assert(!remote_read, "Remote read is not supported in this kernel");

  So in practice ttnn only uses PUSH for halo. Why?

      - PUSH is faster: only one packet per transfer instead of
        request+response.
      - The sender always knows exactly when its source data is ready
        (it owns it). No need to coordinate "is it ready yet?" with the
        receiver.
      - PUSH lets multiple senders fan in to one receiver in parallel.
      - The receiver's NoC unit is freed up for other work.

  From now on, when you see "Core 1 sends its boundary stick to Core 0"
  read it as "Core 1 calls noc_async_write(local_src, core_0_l1_dst,
  size)".


================================================================================
  CHAPTER 3 — THE THREE PER-CORE METADATA TABLES
================================================================================

  Halo is data-driven. The host generates THREE tiny tables per core
  before halo launches and uploads them into each core's L1 (or DRAM).

  Generated by:
      ttnn/cpp/ttnn/operations/sliding_window/sliding_window.cpp
      function `generate_halo_kernel_config_tensors`

  --------------------------------------------------------------------
  TABLE 1: padding_config
  --------------------------------------------------------------------
  "Where in MY output should I write zeros, and how many in a row?"

  Layout (per core), pairs of uint16:

      [ dst_local_idx_0, nsticks_0,
        dst_local_idx_1, nsticks_1,
        ...
        dst_local_idx_K, nsticks_K,
        ?              , 0          <-- terminator: nsticks==0 means end
      ]

  Walked by `copy_padding` in halo_gather.cpp lines 91-111.

  The source for padding is special: every Tensix has a tiny region
  of L1 (`MEM_ZEROS_BASE`) that is hardcoded to all zeros. Halo uses
  noc_async_read from that region to splat zeros into the output.
  (When pad_val != 0, halo first fills a small pad CB with the value
  and uses that as the source instead.)

  --------------------------------------------------------------------
  TABLE 2: local_config (one route per core, "self->self")
  --------------------------------------------------------------------
  "Take these sticks from my OWN input CB and copy them into my OWN
   output CB at these positions."

  Layout (header + transfers):

      header:
          dst_noc_x  = my own NoC x         <-- destination is myself
          dst_noc_y  = my own NoC y
          n_transfers
      transfers (n_transfers of them):
          (src_offset_id, dst_offset_id, transfer_size)

  Walked by `run_halo_gather` in halo_gather.cpp lines 173-236, treated
  identically to a remote route -- the destination NoC address just
  happens to be the same core.

  --------------------------------------------------------------------
  TABLE 3: remote_config (one route PER neighbor that needs my data)
  --------------------------------------------------------------------
  "For each NEIGHBOR core that needs my data, here are the transfers."

  This is the borrowing table. Layout, per route:

      header:
          dst_noc_x          <-- the receiving neighbor's NoC x
          dst_noc_y          <-- the receiving neighbor's NoC y
          n_transfers
      transfers:
          (src_offset_id, dst_offset_id, transfer_size)

  Where:
      src_offset_id  = stick index in MY local input CB
      dst_offset_id  = stick index in the NEIGHBOR's output CB
      transfer_size  = how many consecutive sticks to copy

  ONE COPY OPERATION moves `transfer_size` sticks at once -- the host
  packs adjacent sticks into the same transfer to minimize NoC traffic
  (see lines 727-733 in sliding_window.cpp where it greedily extends
  an existing transfer if `(src_local_idx == src_start + length &&
  local_idx == dst_start + length)`).


================================================================================
  CHAPTER 4 — THE PER-CORE KERNEL: STEP BY STEP
================================================================================

  File: halo_gather.cpp, function kernel_main() (lines 238-334).

  Each core runs the SAME program but reads different config tables.
  The flow on every core:

      1. Untilize own input (if it was tiled).
      2. Run the PADDING phase using padding_config -> own output CB.
      3. Run the GATHER phase using gather_config:
            - Iterate over all routes in the table.
            - For each route, compute the destination NoC address.
            - For each transfer in the route, issue noc_async_write
              from local input to destination L1.
      4. Wait for all writes to drain (noc_async_write_barrier).

  Per-route loop (lines 197-231):

      while (number_of_segments_remaining) {
          dst_noc_x = config[i++];
          dst_noc_y = config[i++];
          transfers_remaining = config[i++];

          out_l1_addr = get_remote_core_l1_noc_addr(dst_noc_x, dst_noc_y, ...);

          while (transfers_remaining > 0) {
              src_offset = config[i++];
              dst_offset = config[i++];
              size       = config[i++];
              write_stick_async(in_base_l1_addr, out_l1_addr,
                                src_offset, dst_offset, size);
              transfers_remaining--;
          }
          number_of_segments_remaining--;
      }

  The actual write call (lines 137-159):

      noc_async_write(src_addr, dst_addr, size_in_bytes);

  The destination address is produced by `get_remote_core_l1_noc_addr`
  (lines 113-134). It packs (noc_x, noc_y, l1_offset) into the 64-bit
  NoC address that the NoC hardware understands.

  Two important details:

      - The DESTINATION L1 offset is the same on every core because all
        cores share the same shard layout: get_write_ptr(OutputCBIndex)
        returns the same offset on every core. So when Core 1 writes
        "address out_base + dst_offset on Core 0", that address is in
        Core 0's L1 output CB.

      - The kernel uses ASYNC writes. They are pipelined; the barrier
        at the end is what waits for completion.


================================================================================
  CHAPTER 5 — A WORKED EXAMPLE: CORE 1 BORROWS-LENDS WITH CORE 0
================================================================================

  Setup (the same one used in 03_sharding_and_halo notes):

      Tensor:  W = 8 sticks, sharded HEIGHT across 4 cores.
      Kernel:  K=3, stride=1, padding=1.

      Before halo (each core's input shard, 2 sticks each):

          Core 0:  [s0, s1]
          Core 1:  [s2, s3]
          Core 2:  [s4, s5]
          Core 3:  [s6, s7]

      Output after halo (each core's output shard, 4 sticks each, layout
      = [pad-or-borrowed | own | borrowed]):

          Core 0:  [P,  s0, s1, s2]      <- Core 1 will push s2
          Core 1:  [s1, s2, s3, s4]      <- Core 0 will push s1, Core 2 will push s4
          Core 2:  [s3, s4, s5, s6]      <- Core 1 will push s3, Core 3 will push s6
          Core 3:  [s5, s6, s7, P]       <- Core 2 will push s5

  Now zoom into Core 1's perspective.

  Core 1 holds inputs [s2, s3] at local input offsets 0, 1.

  Host-generated tables for Core 1:

      padding_config[Core 1]:
          (none -- no pad cells live in Core 1's output)

      local_config[Core 1]   (self -> self):
          dst = Core 1
          transfers:
              (src=0, dst=1, size=1)   # s2 goes to local out slot 1
              (src=1, dst=2, size=1)   # s3 goes to local out slot 2
          (the host packing might combine these into ONE transfer of
           size=2 if src and dst are both contiguous; result is the same)

      remote_config[Core 1]:
          ROUTE A: dst = Core 0
              transfers:
                  (src=0, dst=3, size=1)   # s2 goes to Core 0's out slot 3
          ROUTE B: dst = Core 2
              transfers:
                  (src=1, dst=0, size=1)   # s3 goes to Core 2's out slot 0

  When Core 1 executes the gather kernel:

      1) Loads its tables into the gather_config CB.
      2) Iterates the routes:

         Route LOCAL: dst noc address = Core 1's own NoC coords.
                      noc_async_write copies s2, s3 within own L1.

         Route A:     dst noc address = Core 0's NoC coords.
                      noc_async_write(my_in[0], core0_l1_out[3], 1*stick_bytes)
                      -> s2 lands in Core 0's output slot 3.   <-- THE BORROW

         Route B:     dst noc address = Core 2's NoC coords.
                      noc_async_write(my_in[1], core2_l1_out[0], 1*stick_bytes)
                      -> s3 lands in Core 2's output slot 0.   <-- ANOTHER BORROW

      3) noc_async_write_barrier(): wait for all writes to finish.

  Meanwhile, Core 0 is doing its own gather kernel and pushes s1 to
  Core 1's slot 0, then waits on its own barrier. Eventually all four
  cores have a fully populated output, and the conv2d kernel can run
  with no further NoC traffic.

  Picture of the NoC traffic during halo (arrows = noc_async_write):

         Core 0          Core 1          Core 2          Core 3
            ^               ^               ^               ^
            |               |               |               |
            |  s2 from C1   |  s1 from C0   |  s3 from C1   |  s5 from C2
            +---------------+---------------+               |
                                            |               |
                            +---------------+---------------+
                            |  s4 from C2   |  s6 from C3   |
                            v               v               v


================================================================================
  CHAPTER 6 — HOW THE TABLES ARE BUILT ON THE HOST
================================================================================

  File: sliding_window.cpp, function `generate_halo_kernel_config_tensors`
  (lines 694-803).

  Step-by-step on the host:

      1. For every core, walk over its input region (the range of
         output sticks it needs to fill).

      2. For each output position, look up `tensor_metadata[global_idx]`:
              -> tells you (is_pad, src_core_id, src_local_idx)

      3. Group entries by (src_core_id, dst_core_id):
              - is_pad        -> goes in padding_config[dst_core]
              - src == dst    -> goes in local_config[src_core] (self route)
              - src != dst    -> goes in remote_config[src_core]
                                 (so the SOURCE core knows where to push)

      4. While inserting, GREEDILY EXTEND the previous transfer:

              if src and dst indices are both consecutive:
                  ++length      # bigger transfer, no new entry
              else:
                  start a new triplet (src_start, dst_start, 1)

         This is what makes halo efficient -- multiple adjacent sticks
         become ONE noc_async_write of size N.

      5. Pack each per-core config into a flat uint16 buffer and
         upload it as a circular buffer (or DRAM tensor when
         `config_tensors_in_dram=true`).


================================================================================
  CHAPTER 7 — WHAT ABOUT MULTIPLE BORROWS?
================================================================================

  In a real conv each core borrows from MORE THAN ONE neighbor. Halo
  handles this naturally because remote_config can hold many routes per
  source core.

  Example: kernel = 5, stride = 1, K-1 = 4, so each core needs 4 halo
  sticks total -- 2 from the left neighbor and 2 from the right.

      Core 1 sends 2 sticks to Core 0, 2 sticks to Core 2.
      Core 0 receives 2 sticks from Core 1.
      Core 2 receives 2 sticks from Core 1, 2 from Core 3.
      ...

  The kernel just iterates routes; it does not care how many.

  For BLOCK_SHARDED tensors, each core may also send to cores in a
  different ROW of the chip grid (because the height-axis neighbor is
  one row up/down on the physical mesh). The host handles all this in
  `core_id_to_noc_coords` (sliding_window.cpp:704-709) which maps
  logical core IDs to physical NoC (x, y) coordinates.


================================================================================
  CHAPTER 8 — SPECIAL CASE: PAD ZEROS
================================================================================

  Pad cells are not borrowed from any core; they are filled from
  MEM_ZEROS_BASE -- a small constant-zero region built into every
  Tensix's L1.

  Lines 295-310 of halo_gather.cpp:

      if constexpr (pad_val_u32 == 0) {
          // Use MEM_ZEROS_BASE (always-zero L1 region)
          const uint64_t padding_l1_addr =
              get_noc_addr(my_noc_x, my_noc_y, MEM_ZEROS_BASE);
          ...
          copy_padding<...>(padding_l1_addr);
      } else {
          // Build a small CB with the requested pad value, then copy from there
          fill_with_val<num_elements_to_fill, pad_val>(get_write_ptr(pad_cb_id));
          ...
      }

  So even pad sticks use a noc_async_read (from a same-core address)
  rather than a memset. This keeps the data path uniform with the
  borrow path.


================================================================================
  CHAPTER 9 — TIMELINE: WHAT HAPPENS WHEN
================================================================================

  Halo is one barrier-bounded phase. The host launches the kernel on
  ALL participating cores at the same time. Each core runs:

      t=0     -- enter kernel_main
      t=1     -- pad phase: copy zeros into own output (parallel; same core)
      t=2     -- gather phase: iterate routes; for each:
                     - LOCAL: noc_async_write within self
                     - REMOTE: noc_async_write to neighbor
                 All async, pipelined.
      t=3     -- noc_async_write_barrier(): wait for OWN sends to finish
      t=4     -- noc_async_read_barrier():  wait for any incoming reads
      t=END   -- kernel_main returns; halo output is ready

  Critically the receiver does NOT issue an explicit "wait for incoming
  writes" call. Instead each sender waits for its writes to land
  (with `noc_async_write_barrier`), which on Wormhole's NoC means the
  data has been delivered to the destination L1. Once every core has
  cleared its own barrier, the global halo is complete (the conv2d
  kernel that follows depends on this barrier, enforced by the runtime).


================================================================================
  CHAPTER 10 — FAQ
================================================================================

  Q: How does Core 0 know "my slot 3 is the borrow from Core 1"?
  A: It does not. The transfer offsets are decided by the HOST at
     compile/launch time. Core 0 just sees data appear in its
     output CB at the address Core 1 wrote to.

  Q: What if Core 0 starts reading the halo output before Core 1
     finishes writing?
  A: It cannot. The halo is a separate program from conv2d; the
     runtime inserts a barrier. Conv2d does not start until every
     core's halo kernel has returned.

  Q: Is the borrow limited to nearest neighbors?
  A: Logically yes for HEIGHT_SHARDED (kernel of size K can reach at
     most ceil((K-1)/2) sticks beyond shard edges). Physically the
     NoC routes any (x,y)->(x',y') with multi-hop paths if needed.
     The kernel does not care.

  Q: What is the NoC cost of borrowing one stick?
  A: One noc_async_write packet. Wormhole NoC packets have a fixed
     header overhead plus payload cost. Borrowing many adjacent
     sticks in one packet (transfer_size > 1) amortizes the header.

  Q: What happens for "DRAM-sliced" conv_transpose2d?
  A: Each slice goes through its own halo phase, with its own freshly
     computed tables. The borrow mechanism is identical, just over a
     smaller per-slice tensor.

  Q: Can a core borrow from itself?
  A: That is what the LOCAL route is for. The src_core==dst_core route
     uses the same noc_async_write but the destination NoC address
     happens to be the core's own coordinates -- a "loopback" write.


================================================================================
  CHAPTER 11 — RECAP
================================================================================

  Halo "borrowing" is not a borrow. It is a PUSH:

      Core 1 (the source/owner) calls noc_async_write to copy its
      stick(s) directly into the L1 output CB of Core 0 (the consumer).

  Three on-core tables drive the kernel:

      padding_config -> where to splat zeros
      local_config   -> self -> self transfers (own sticks)
      remote_config  -> self -> neighbor transfers (the actual borrow)

  Tables are built on the host by `generate_halo_kernel_config_tensors`
  (sliding_window.cpp). The host greedily packs adjacent sticks into
  a single transfer to amortize NoC packet overhead.

  Each core runs the SAME halo kernel but with its own tables. After
  the per-core write barrier, every output CB on every core is
  populated and the conv2d kernel can run with zero NoC traffic during
  compute.
