This note zooms in on a single 27-line block of the polyphase orchestrator:

    File: ttnn/cpp/ttnn/operations/conv/conv_transpose2d/
              conv_transpose2d_polyphase.cpp
    Lines: 200..226

It's the "post-conv2d cleanup" block. Every per-phase iteration runs it,
and during bring-up it was the source of the PCC = 0.097 disaster (see
note 11 bug 4). Worth understanding line by line, with a concrete
worked example.

We'll use the tiny_k8_s4 shape (consistent with notes 13 and the
correctness test):

    N    = 1     (batch)
    C_in = 1     (input channels)
    C_out= 1     (output channels)
    T_in = 8     (input width)
    K_w  = 8     (kernel width)
    S_w  = 4     (stride width)
    K_p  = 2     (per-phase kernel = ceil(K_w/S_w))
    T_phase = T_in + K_p - 1 = 9     (per-phase output length)

We're inside the for-loop, looking at phase = 0.

We will walk through it as 4 numbered steps and show the tensor state
BEFORE and AFTER each one.

--------------------------------------------------------------------------------
STEP 1  (line 200)   -- unwrap the std::variant returned by ttnn::conv2d
--------------------------------------------------------------------------------

    ttnn::Tensor phase_out = std::get<ttnn::Tensor>(conv_result);

BEFORE (conv_result):
    Type: ttnn::Conv2dResultWithOptions
          (a std::variant<Tensor,
                          tuple<Tensor, dims>,
                          tuple<Tensor, weights>,
                          tuple<Tensor, dims, weights>>)
    Active alternative for us: just `Tensor`

    Why "just Tensor"? Because we called ttnn::conv2d with
       return_output_dim = false
       return_weights_and_bias = false
    so the variant carries the plain Tensor alternative.

AFTER:
    phase_out: ttnn::Tensor
        logical_shape : Shape([1, 1, 9, 1])
        layout        : Layout::TILE
        memory_config : sharded across cores, L1
        dtype         : bfloat16

  This is a pure type-system unwrap. NO data movement, NO device work.
  All it does is "extract the Tensor from the variant container".

  The logical shape (1, 1, 9, 1) is correct (NHWC with H=1, W=T_phase=9,
  C=C_out=1) -- but its PHYSICAL storage on the device is laid out very
  differently because of the TILE + sharded combination. That mismatch is
  what the next two steps fix.

--------------------------------------------------------------------------------
STEP 2  (lines 207-213)   -- sharded -> interleaved DRAM (conditional)
--------------------------------------------------------------------------------

    if (phase_out.memory_config().is_sharded()) {
        phase_out = ttnn::sharded_to_interleaved(
            phase_out,
            tt::tt_metal::MemoryConfig{
                tt::tt_metal::TensorMemoryLayout::INTERLEAVED,
                tt::tt_metal::BufferType::DRAM});
    }

BEFORE:
    phase_out (from STEP 1):
        logical_shape : (1, 1, 9, 1)
        layout        : Layout::TILE
        memory_config : SHARDED across multiple cores' L1 buffers
                        e.g. core (0,0) holds rows 0..3,
                             core (0,1) holds rows 4..8, etc.

    Why sharded? Because ttnn::conv2d's default output placement spreads
    the result across cores so the next op can consume it in parallel.
    But that placement is opaque to a generic reshape/concat -- those
    ops want a single contiguous logical tensor.

AFTER:
    phase_out:
        logical_shape : (1, 1, 9, 1)             <- UNCHANGED
        layout        : Layout::TILE             <- UNCHANGED
        memory_config : INTERLEAVED in DRAM      <- CHANGED
        dtype         : bfloat16                 <- UNCHANGED

    The actual values are the same; only their LOCATION changed (cores'
    L1 -> DRAM, with the interleaved address pattern that ttnn data-
    movement ops know how to read).

  Why we need this:
      Most data-movement ops (reshape, concat, slice) are written
      assuming an interleaved tensor. They cannot reason about the
      core-by-core shard placement directly. So if we skipped this
      step we would crash (or get silently wrong output) inside
      ttnn::concat with a "shard layout mismatch" error.

  Why the IF guard:
      Not every conv2d output is sharded -- some configurations
      already produce interleaved tensors. The guard avoids a
      pointless copy in that case.

  Cost:
      One DRAM-bound copy of (1, 1, 9, 1) bfloat16 elements
      (a few hundred bytes in this tiny example, scales linearly
      with the per-phase output size for bigger shapes).

--------------------------------------------------------------------------------
STEP 3  (lines 214-223)   -- TILE -> ROW_MAJOR (conditional)
--------------------------------------------------------------------------------

    if (phase_out.layout() != Layout::ROW_MAJOR) {
        phase_out = ttnn::to_layout(
            phase_out,
            Layout::ROW_MAJOR,
            /*dtype=*/std::nullopt,
            /*memory_config=*/
            tt::tt_metal::MemoryConfig{
                tt::tt_metal::TensorMemoryLayout::INTERLEAVED,
                tt::tt_metal::BufferType::DRAM});
    }

BEFORE:
    phase_out (from STEP 2):
        logical_shape : (1, 1, 9, 1)
        layout        : Layout::TILE             <- still tile-organized
        memory_config : INTERLEAVED in DRAM
        dtype         : bfloat16

    What "TILE" really means:
        On Tensix the smallest unit of compute is a 32x32 tile.
        A logical (1, 1, 9, 1) tensor in TILE layout is physically
        stored as ONE 32x32 tile in which:
            - rows 0..8   hold the 9 real W values
            - rows 9..31  hold ZERO PADDING
            - cols 0..0   hold the 1 real C value
            - cols 1..31  hold ZERO PADDING

        Schematically (rows are NHW-flat, cols are C):

            col idx    0   1   2  ...  31
                     +---+---+---+-----+---+
            row  0   | v0| 0 | 0 | ... | 0 |   <- real value at logical W=0
            row  1   | v1| 0 | 0 | ... | 0 |   <- real value at logical W=1
            row  2   | v2| 0 | 0 | ... | 0 |
              :      | : | 0 | 0 | ... | 0 |
            row  8   | v8| 0 | 0 | ... | 0 |
            row  9   | 0 | 0 | 0 | ... | 0 |   <- pure padding from here down
            row 10   | 0 | 0 | 0 | ... | 0 |
              :      | : | : | : | ... | : |
            row 31   | 0 | 0 | 0 | ... | 0 |
                     +---+---+---+-----+---+

        The 32x32 = 1024 cells are stored CONTIGUOUSLY in memory in a
        tile-internal serpentine order. Of those 1024 cells, only 9
        carry real data.

AFTER:
    phase_out:
        logical_shape : (1, 1, 9, 1)             <- UNCHANGED
        layout        : Layout::ROW_MAJOR        <- CHANGED
        memory_config : INTERLEAVED in DRAM       <- UNCHANGED
        dtype         : bfloat16

    What "ROW_MAJOR" means:
        Physical storage matches the logical shape EXACTLY, with no
        padding. (1, 1, 9, 1) is 1*1*9*1 = 9 contiguous bfloat16
        elements:

            offset 0    1    2    3    4    5    6    7    8
                  +----+----+----+----+----+----+----+----+----+
                  | v0 | v1 | v2 | v3 | v4 | v5 | v6 | v7 | v8 |
                  +----+----+----+----+----+----+----+----+----+

        That's it. No padding, no serpentine, no surprises.

  Why we MUST do this conversion:
      The next steps reshape (1,1,9,1) -> (1,9,1,1), concat 4 such
      tensors along dim=2, reshape to (1,1,36,1), and slice.

      Those data-movement ops compute their output addresses based on
      the LOGICAL shape and a flat ROW_MAJOR stride formula. They
      have NO awareness of the 32x32 tile structure. If you feed them
      a TILE tensor, the (padded) elements at rows 9..31 get
      re-interpreted as real data, and the order of v0..v8 gets
      scrambled because the tile-internal serpentine doesn't match
      simple flat row-major addressing.

      That is exactly the bug we hit during bring-up -- PCC = 0.097.
      Notes 11 section 5 bug 4 and 08 section "debug session" cover
      the diagnostic story.

  Why the IF guard:
      to_layout(ROW_MAJOR) on an already-row-major tensor is a no-op
      but still costs a function-call check. Cheap protective gate
      that lets V2 reorderings drop this step without breaking V1.

  Cost:
      One DRAM-bound TILE -> ROW_MAJOR conversion. For a (1,1,9,1)
      tensor: read 1024 bf16 cells of a tile, write 9 bf16 cells of
      row-major. That's ~2KB read / 18B write per phase. For the
      iSTFT envelope shape with T_phase = 99 it would be 1 tile read
      (because 99 < 32*4 -> 4 tiles tall) and 198 bytes written.
      Negligible compared to the conv2d itself.

COUNTER-EXAMPLE: WHAT THE SAME NUMBERS LOOK LIKE WITHOUT THIS BLOCK
--------------------------------------------------------------------------------

If we comment out STEPs 2 and 3 (keep the variant unwrap, skip the
two layout coercions), the bug manifests like this for the SAME inputs:

  phase_out is still TILE+sharded (1,1,9,1) when we hand it to
  ttnn::reshape((1,9,1,1)). reshape doesn't touch the bytes; it only
  changes the shape metadata. So the tile padding zeros at original
  rows 9..31 still sit in physical memory.

  Then ttnn::concat(dim=2) reads four such tensors using flat
  row-major addressing. For each output position p it computes
  some byte offset and pulls the bf16 sitting there. The "tile
  padding zero" rows now get read as if they were real W positions,
  scrambling the interleave.

  The actual numbers we observed for this case (see your earlier
  failing test output):

--------------------------------------------------------------------------------
PUTTING IT ALL TOGETHER - WHAT THIS BLOCK ACCOMPLISHES
--------------------------------------------------------------------------------

  Input (from ttnn::conv2d):
      Tensor inside a variant container.
      Shape (1, 1, 9, 1)  -- correct.
      Layout TILE         -- WRONG for downstream interleave.
      Memory SHARDED      -- WRONG for downstream interleave.

  Output (pushed into phase_outputs):
      Bare Tensor (no variant).
      Shape (1, 1, 9, 1)  -- same.
      Layout ROW_MAJOR    -- right for interleave.
      Memory INTERLEAVED DRAM -- right for interleave.

  Net effect: same logical values, but in a layout/memory_config
  that the next reshape+concat+slice chain can safely consume.

  Cost per phase: 2 cheap data-movement copies (sharded->interleaved
  and TILE->ROW_MAJOR), both DRAM-bandwidth bound. For the iSTFT
  shape (S_w=160) the cumulative cost is still small compared to
  the 160 actual conv2ds. For tiny shapes it's a wash.

--------------------------------------------------------------------------------
WHAT WOULD HAPPEN IF WE SKIPPED THIS BLOCK ENTIRELY?
--------------------------------------------------------------------------------

  We did exactly that during bring-up. The symptoms:

    1) ttnn::reshape((1,1,9,1) -> (1,9,1,1)) on a TILE tensor
       does NOT physically rearrange data. It only updates the
       logical shape metadata. So the 32x32 tile's serpentine
       addressing now maps to the wrong logical (N,T_phase,1,C)
       coordinates.

    2) ttnn::concat along dim=2 of four such tensors reads
       elements assuming row-major addressing. For each output
       position it grabs whatever element happens to lie at the
       computed offset -- which is mostly PADDING (rows 9..31)
       mixed with whatever real values happen to overlap.

    3) The final (1,1,36,1) tensor contains a roughly
       random-looking mix of real values and tile padding zeros.

    4) PCC against PyTorch reference: 0.0978.

  Reinstating the sharded_to_interleaved + to_layout(ROW_MAJOR)
  steps brought PCC up to 0.99+ across all test shapes. See note 11
  section 5 bug 4 for the full debug story.
