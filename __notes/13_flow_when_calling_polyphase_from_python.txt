This note traces, step by step, exactly what happens from the moment you
type:

    out = ttnn.experimental.conv_transpose2d_polyphase(
        input_tensor=x_tt,
        weight_tensor=w_tt,
        device=device,
        in_channels=1, out_channels=1,
        batch_size=1, input_height=1, input_width=8,
        kernel_size=(1, 8), stride=(1, 4),
        padding=(0, 0), output_padding=(0, 0),
        dilation=(1, 1), groups=1,
        mirror_kernel=True,
    )

...to the moment a finished tensor is handed back. Every function and file
that gets hit, in order.

We use the tiny_k8_s4 shape (K_w=8, S_w=4, T_in=8, C_in=C_out=1) as a
running example so the numbers stay concrete.

--------------------------------------------------------------------------------
0. WHAT THE PYTHON-LEVEL ATTRIBUTE EVEN IS
--------------------------------------------------------------------------------

`ttnn.experimental.conv_transpose2d_polyphase` is a Python attribute created
at IMPORT TIME, not at call time. It lives on the `ttnn.experimental`
module because of the nanobind glue we registered.

  Created in:
      ttnn/cpp/ttnn/operations/experimental/conv_transpose2d_polyphase/
          conv_transpose2d_polyphase_nanobind.cpp     (lines 67-93)

      ttnn::bind_function<"conv_transpose2d_polyphase", "ttnn.experimental.">(
          mod, doc,
          &ttnn::operations::experimental::conv_transpose2d_polyphase::
              conv_transpose2d_polyphase,
          nb::kw_only(),
          nb::arg("input_tensor"), nb::arg("weight_tensor"), ...);

  Invoked once at ttnn-module init from:
      ttnn/cpp/ttnn/operations/experimental/experimental_nanobind.cpp
          -> bind_experimental_conv_transpose2d_polyphase(mod);

So by the time Python user code does `import ttnn`, the function is already
sitting in ttnn.experimental and ready to be called.

--------------------------------------------------------------------------------
1. PYTHON CALL CROSSES INTO C++ (NANOBIND)
--------------------------------------------------------------------------------

  Python side                                        C++ side hit
  ----------------------------------------          ----------------------------
  ttnn.experimental.                                 nanobind trampoline (auto-
       conv_transpose2d_polyphase(...)               generated by bind_function)

What nanobind does for us:
  - Converts Python kw-args -> C++ types listed in the nb::arg(...) chain.
  - Converts None -> std::nullopt for optional args.
  - Auto-wraps tuples like (1, 8) into std::array<uint32_t, 2>.
  - Auto-wraps (T, B, L, R) shapes into the std::variant<arr2, arr4> for
    padding.
  - GIL is released around the C++ call (so other Python threads can run).

It then calls the actual C++ function whose pointer we registered:

    &ttnn::operations::experimental::conv_transpose2d_polyphase::
         conv_transpose2d_polyphase

That points at the experimental-wrapper file - the next stop in the chain.

--------------------------------------------------------------------------------
2. EXPERIMENTAL WRAPPER (THIN FORWARDER)
--------------------------------------------------------------------------------

  File: ttnn/cpp/ttnn/operations/experimental/conv_transpose2d_polyphase/
            conv_transpose2d_polyphase.cpp

  Function (lines 34-79):
      ttnn::ConvTranspose2dResultWithOptions conv_transpose2d_polyphase(
          ...all the same args... ,
          bool return_output_dim,
          bool return_weights_and_bias) {
          auto result = impl::conv_transpose2d_polyphase(... forward ...);
          return to_result_with_options(
              result, return_output_dim, return_weights_and_bias);
      }

  What it does:
    a) Forwards every argument unchanged to the CORE orchestrator in the
       non-experimental namespace:
          impl  ==  ttnn::operations::conv::conv_transpose2d
    b) The core orchestrator returns a 5-tuple ConvTranspose2dResult.
    c) to_result_with_options(...) (lines 15-30) repackages that into the
       variant return type that matches the user's return_output_dim and
       return_weights_and_bias flags:
            both false  -> just ttnn::Tensor
            dim only    -> (tensor, (OH, OW))
            weights only-> (tensor, (weight, bias))
            both true   -> (tensor, (OH, OW), (weight, bias))

  So this file's only job is type re-packaging + namespace forwarding. It
  contains zero algorithm logic.

--------------------------------------------------------------------------------
3. CORE ORCHESTRATOR - THE ACTUAL ALGORITHM
--------------------------------------------------------------------------------

  File: ttnn/cpp/ttnn/operations/conv/conv_transpose2d/
            conv_transpose2d_polyphase.cpp

  Function (line 75):
      ConvTranspose2dResult conv_transpose2d_polyphase(...)

  This is where polyphase actually happens. Walking through it:

== 3.1  Padding-spec normalization (lines 101-105) ==

      const auto padding_n4 = sliding_window::get_pair_n4_padding(padding_);
      const uint32_t pad_top    = padding_n4[0];
      const uint32_t pad_bottom = padding_n4[1];
      const uint32_t pad_left   = padding_n4[2];
      const uint32_t pad_right  = padding_n4[3];

  Calls into:
      ttnn/cpp/ttnn/operations/sliding_window/sliding_window.cpp
          -> get_pair_n4_padding(...)

  Just converts the std::variant<arr2, arr4> padding into a flat 4-element
  array. No device ops.

== 3.2  V1 precondition checks (lines 107-114) ==

      TT_FATAL(input_height == 1, ...);
      TT_FATAL(kernel_size[0] == 1, ...);
      TT_FATAL(stride[0] == 1, ...);
      TT_FATAL(dilation[0] == 1 && dilation[1] == 1, ...);
      TT_FATAL(groups == 1, ...);
      TT_FATAL(pad_top == 0 && pad_bottom == 0, ...);
      TT_FATAL(pad_left == 0 && pad_right == 0, ...);
      TT_FATAL(output_padding[0] == 0 && output_padding[1] == 0, ...);

  If any of these is violated -> crash here, before any device work
  happens.

  For our tiny_k8_s4 example:
      input_height = 1     OK
      kernel_size  = (1, 8) -> kernel_h = 1 OK
      stride       = (1, 4) -> stride_h = 1 OK
      dilation     = (1, 1) OK
      groups       = 1 OK
      padding      = (0, 0) OK
      output_padding = (0, 0) OK

== 3.3  Derived parameters (lines 116-122) ==

      const uint32_t k_w   = kernel_size[1];          //  = 8
      const uint32_t s_w   = stride[1];               //  = 4
      const uint32_t k_p   = (k_w + s_w - 1) / s_w;   //  = ceil(8/4) = 2
      const uint32_t t_in  = input_width;             //  = 8
      const uint32_t t_out = (t_in - 1) * s_w + k_w;  //  = 7*4 + 8 = 36

  These define the V1 shape contract:
      number of phases     = s_w = 4
      per-phase kernel     = k_p = 2
      per-phase output T   = t_in + k_p - 1 = 9
      final output T       = t_out = 36

== 3.4  Host-side weight shuffle (lines 128-137) ==

      ttnn::Tensor weight_host =
          tt::tt_metal::is_device_tensor(weight_tensor)
              ? ttnn::operations::core::from_device(weight_tensor)
              : weight_tensor;
      ttnn::Tensor shuffled_weights =
          shuffle_weights_polyphase(weight_host, s_w);

  Calls:
    - tt::tt_metal::is_device_tensor(...)          [predicate]
    - ttnn::operations::core::from_device(...)     [DEVICE -> HOST copy, only if needed]
    - shuffle_weights_polyphase(...)               [host-side compute]

  shuffle_weights_polyphase is in:
      ttnn/cpp/ttnn/operations/conv/conv_transpose2d/
          prepare_conv_transpose2d_weights.cpp        (lines 230-300)

  What it does (one pass over the weight buffer):
    - takes IOHW input [C_in, C_out, 1, K_w] = [1, 1, 1, 8]
    - emits OIHW output [S_w, C_out, C_in, 1, K_p] = [4, 1, 1, 1, 2]
    - Each phase p's K_p slice is filled with:
          out[p, c_out, c_in, 0, kp] = w[c_in, c_out, 0,
                                         phase + (K_p - 1 - kp) * S_w]
    - The (K_p - 1 - kp) reversal bakes in the cross-correlation reversal
      that ttnn::conv2d expects.

  For our tiny example, the 8 weights are split into 4 sub-kernels of 2
  weights each:
      phase 0 sub-kernel:  [ w[4], w[0] ]
      phase 1 sub-kernel:  [ w[5], w[1] ]
      phase 2 sub-kernel:  [ w[6], w[2] ]
      phase 3 sub-kernel:  [ w[7], w[3] ]

  This is the ONE place where the polyphase math lives. The rest is just
  scheduling.

== 3.5  Padding bookkeeping (lines 151-154) ==

      const uint32_t conv_pad_left  = k_p - 1;     // = 1
      const uint32_t conv_pad_right = k_p - 1;     // = 1
      const std::array<uint32_t, 4> conv_padding_n4 = {0u, 0u, 1u, 1u};

  This is the symmetric "same" padding we pass to ttnn::conv2d directly
  (NOT to ttnn::pad). Putting K_p-1 zeros on each side of W is what
  makes each phase produce exactly T_in + K_p - 1 outputs.

== 3.6  Per-phase loop (lines 167-226) ==

  This is the hot loop. For each phase p = 0..S_w-1 it does:

    a) phase_w = slice_phase_weights(shuffled_weights, p);
         -- defined locally in the same file (lines 32-72)
         -- host memcpy from the [S_w, ...] tensor into a standalone
            [C_out, C_in, 1, K_p] OIHW tensor

    b) ttnn::conv2d(input_tensor, phase_w, device, ...,
                    kernel_size = {1, k_p},
                    stride      = {1, 1},
                    padding     = conv_padding_n4,
                    dilation    = {1, 1}, groups = 1, bias = bias_for_call,
                    ...);
         -- THIS IS THE DEVICE-SIDE COMPUTE. Everything we've done up to
            now was on host (or trivial metadata twiddling).
         -- File: ttnn/cpp/ttnn/operations/conv/conv2d/conv2d.cpp
         -- Returns a Conv2dResultWithOptions (a std::variant). We
            requested the plain-tensor variant via
            return_output_dim=false, return_weights_and_bias=false.

    c) phase_out = std::get<ttnn::Tensor>(conv_result);

       If conv2d returned a sharded TILE tensor (which it usually does):
         phase_out = ttnn::sharded_to_interleaved(phase_out, ...);
            -- File: ttnn/cpp/ttnn/operations/data_movement/sharded/
                         sharded_to_interleaved/sharded_to_interleaved.cpp

         phase_out = ttnn::to_layout(phase_out, Layout::ROW_MAJOR, ...);
            -- File: ttnn/cpp/ttnn/operations/core/to_layout/
                         to_layout_op.cpp

       These two coercions are what make the downstream reshape+concat
       behave correctly. Without them, TILE-internal padding scrambles
       the W axis when we reshape (we hit PCC = 0.097 from this during
       bring-up; see note 11 bug 4).

    d) phase_outputs.push_back(std::move(phase_out));

  For tiny_k8_s4, this loop fires 4 times. For the iSTFT envelope shape
  it fires 160 times.

  IMPORTANT V1 GAP (line 170-172):
      bias_for_call is set to bias_tensor ONLY for phase 0. Other phases
      get std::nullopt. For shapes WITH bias this produces wrong output
      (only 1/S_w of positions get bias). Fix: route bias to every
      phase. See note 11 section 6.

== 3.7  Per-phase reshape (lines 261-274) ==

      for (auto& po : phase_outputs) {
          // (N, 1, T_phase, C) -> (N, T_phase, 1, C)
          ttnn::Shape new_shape{n, w, 1u, c};
          reshaped_phases.push_back(ttnn::reshape(po, new_shape));
      }

  Calls:
    - ttnn::reshape(...)
      File: ttnn/cpp/ttnn/operations/data_movement/reshape_view/reshape.cpp

  Inserts a new singleton axis where the "phase" axis will live after
  concat. On ROW_MAJOR tensors this is metadata-only (no copy).

== 3.8  Concat - this is THE interleave (line 277) ==

      ttnn::Tensor stacked = ttnn::concat(reshaped_phases, /*dim=*/2);

  Calls:
    - ttnn::concat(...)
      File: ttnn/cpp/ttnn/operations/data_movement/concat/concat.cpp

  Produces shape (N, T_phase, S_w, C). Because S_w is now the fast axis
  immediately before C, flattening (T_phase, S_w) into a single W axis
  in the next step naturally lays elements out as:

      [phase_0[0], phase_1[0], ..., phase_{S-1}[0],
       phase_0[1], phase_1[1], ..., phase_{S-1}[1], ...]

  which is exactly y[t] = phase_p[j], with t = j*S + p.

  For tiny_k8_s4:  (1, 9, 1, 1) x 4  ->  (1, 9, 4, 1)

== 3.9  Final flatten + slice (lines 280-297) ==

      ttnn::Tensor flattened = ttnn::reshape(stacked, {n, 1u, merged_t, c});
      if (merged_t > t_out) {
          output = ttnn::slice(flattened, begins, ends, steps);
      } else {
          output = flattened;
      }

  Calls:
    - ttnn::reshape(...)   (same file as 3.7)
    - ttnn::slice(...)
      File: ttnn/cpp/ttnn/operations/data_movement/slice/slice.cpp

  merged_t = T_phase * S_w = 9 * 4 = 36. For our example, merged_t ==
  t_out so the slice branch is NOT taken. For shapes where K_w is not
  a multiple of S_w you can end up with a few "tail" extra samples
  that the slice trims off.

== 3.10  Return tuple build (line 299) ==

      return ConvTranspose2dResult{output, 1, t_out,
                                   first_weight_on_device,
                                   first_bias_on_device};

  ConvTranspose2dResult is just a std::tuple typedef defined in
  ttnn/cpp/ttnn/operations/conv/conv_transpose2d/conv_transpose2d.hpp.

  At this point we hand control back to the experimental wrapper
  (step 2), which repackages this into a Python-friendly type and
  returns to the nanobind trampoline.

--------------------------------------------------------------------------------
4. CONTROL FLOW BACK TO PYTHON
--------------------------------------------------------------------------------

  step 3.10  return ConvTranspose2dResult ----> step 2 (wrapper)
  step 2      to_result_with_options(...)  ----> nanobind trampoline
  trampoline  C++ tuple -> Python tuple/Tensor
              re-acquires GIL
              hands the result back to user Python code

For our test invocation (return_output_dim=false, return_weights_and_bias=false)
the user simply gets a single ttnn.Tensor of shape (1, 1, 36, 1).

--------------------------------------------------------------------------------
5. END-TO-END FILE TRAVERSAL ORDER (cheatsheet)
--------------------------------------------------------------------------------

In order, the files actually touched by one polyphase call:

  1. ttnn/cpp/ttnn/operations/experimental/conv_transpose2d_polyphase/
         conv_transpose2d_polyphase_nanobind.cpp        [nanobind glue]

  2. ttnn/cpp/ttnn/operations/experimental/conv_transpose2d_polyphase/
         conv_transpose2d_polyphase.cpp                 [experimental wrapper]

  3. ttnn/cpp/ttnn/operations/conv/conv_transpose2d/
         conv_transpose2d_polyphase.cpp                 [core orchestrator]

  4. ttnn/cpp/ttnn/operations/sliding_window/
         sliding_window.cpp                             [padding normalization]

  5. ttnn/cpp/ttnn/operations/conv/conv_transpose2d/
         prepare_conv_transpose2d_weights.cpp           [shuffle_weights_polyphase]

  Then, INSIDE the per-phase loop, for each phase:

  6. ttnn/cpp/ttnn/operations/core/core.cpp             [is_device_tensor / from_device, only
                                                          if weights start on device]

  7. ttnn/cpp/ttnn/operations/conv/conv2d/
         conv2d.cpp                                     [ttnn::conv2d - the actual compute]

  8. ttnn/cpp/ttnn/operations/data_movement/sharded/
         sharded_to_interleaved/sharded_to_interleaved.cpp   [layout coercion 1]

  9. ttnn/cpp/ttnn/operations/core/to_layout/
         to_layout_op.cpp                               [layout coercion 2: TILE -> ROW_MAJOR]

  After the loop:

 10. ttnn/cpp/ttnn/operations/data_movement/reshape_view/
         reshape.cpp                                    [per-phase reshape, x S_w]

 11. ttnn/cpp/ttnn/operations/data_movement/concat/
         concat.cpp                                     [the interleave]

 12. ttnn/cpp/ttnn/operations/data_movement/reshape_view/
         reshape.cpp                                    [final flatten]

 13. ttnn/cpp/ttnn/operations/data_movement/slice/
         slice.cpp                                      [optional T_out trim]

That's the complete tour. Eight production ttnn ops + one host weight
shuffle, glued together by ~300 lines of orchestrator. No new device
kernels, no halo, no zero-interleaving.
